## 1. 재현 및 렌더러 비교

* 입력 스크립트(`--max-vblanks 3900`): 첫 곡(DISC 01 `바람에게 부탁해`) 진입 후 `GAME OVER`를 거쳐 `1st.STAGE` 선곡 화면으로 돌아와 `RIGHT` + `CIRCLE`로 두 번째 곡(DISC 02 `Luv Flow`)을 선택해 표지(아이캐치) 화면까지 진행했다.
* **렌더러 비교**:
  * `--renderer sw`: 첫 곡 표지 정상, 두 번째 곡 표지(`frame_1452.bmp`)도 **`Luv Flow`**로 정상 출력.
  * `--renderer gl` (수정 전): 두 번째 곡 디스크 확대까지는 `Luv Flow`이나, 곡 선택 직후 나오는 전체 화면 곡 표지(아이캐치, `frame_2478.bmp`)에 첫 번째 곡 **`바람에게 부탁해`**가 그대로 출력됨.
  * 결론: 이미지 재적재·디코드 경로가 아니라 **GL 텍스처 캐시** 계층의 결함.

## 2. 원인 및 근거

* OpenGL 백엔드([gl_backend.cpp](../../third_party/repsp/src/gpu/gl_backend.cpp)) `ResolveTextureLocked()`에서 `st.tex_w >= 256 && st.tex_h >= 256` 업로드 로그를 확인한 결과, User RAM(`0x08000000..0x0A000000`)에 있는 비-CLUT(`fmt=1` ABGR1555, `fmt=2` ABGR4444, `fmt=3` ABGR8888) 텍스처들의 `content_hash`가 모두 **`0x0000000000000000`**으로 계산되고 있었다.
  * 예: `addr=0x08C4DA60 w=512 h=256 bw=512 fmt=1 swz=1 bytes=262144 hash=0x0000000000000000`, `addr=0x08DC1F50 w=512 h=256 bw=512 fmt=2 swz=1 bytes=262144 hash=0x0000000000000000`, `addr=0x09219110 w=512 h=256 bw=512 fmt=3 swz=1 bytes=524288 hash=0x0000000000000000`.
* **원인 (`HashGuestRange` in `gl_backend.cpp`)**:
  * `if (addr >= runtime::GuestMemory::kVramAddress)` 조건에 상한 검사가 없어, `0x04000000`보다 큰 **모든 User RAM 주소(`0x08xxxxxx`~`0x09xxxxxx`)**가 VRAM 범위 초과 판정(`off > kVramSize`)에 걸려 `0`을 반환했다.
  * CLUT 텍스처(`fmt=5` 등)만 뒤이어 CLUT 테이블을 해시해 `content_hash != 0`이 되었고, 비-CLUT 텍스처(곡 표지 아이캐치 포함)는 전부 `content_hash == 0`으로 저장되어 같은 주소·크기·형식으로 두 번째 곡 이미지가 덮어씌워져도 `0 == 0`으로 캐시 적중되었다.

## 3. 수정 및 합성 프로브

* **`HashGuestRange` 수정 (`third_party/repsp/src/gpu/gl_backend.cpp`)**: `GuestMemory::IsValidAddress(addr, size)`로 유효 영역(Scratchpad/VRAM/Kernel/User RAM 및 미러 폴딩)을 검사한 뒤 `Translate(addr)`을 FNV-1a 해시하도록 고쳤다.
* **합성 프로브 (`third_party/repsp/tools/gl_probe/main.cpp`)**: User RAM(`0x08900000`)에 16×16 `ABGR8888`(`fmt=3`) 텍스처를 빨간색(`0xFF0000FF`)으로 그린 뒤, 같은 주소·형식·크기에 초록색(`0xFF00FF00`)으로 덮어쓰고 다시 그려 픽셀이 초록색으로 갱신되는지 검증한다(수정 전 실패, 수정 후 통과).

## 5. 후속 조사: 아이캐치 → 플레이 전환 노이즈 프레임 (#43b)

* **현상 및 렌더러 비교 (`--renderer sw` vs `--renderer gl`)**:
  * 아이캐치(곡 표지) 화면에서 플레이 화면으로 전환되는 직전 순간에, 플레이 화면 UI 텍스처 아틀라스(`COOL`/`GOOD`/`MAX`/`BREAK` 등)가 화면 전체 크기에 잘못된 형식으로 그려진 노이즈 프레임이 나타난다.
  * 두 곡 연속 입력 스크립트로 덤프한 결과, `--renderer sw`(`frame_1453.bmp`)와 `--renderer gl`(`frame_2324.bmp`) **모두에서 동일한 노이즈 프레임이 재현**되었다(GL 백엔드 고유 결함이 아님).
* **추적 근거 (`GeInterpreter`, `hle_display`, `iofilemgr`, `hle_dmac`, `REPSP_HLE_TRACE`)**:
  1. 아이캐치 표시 시점: `sceGeListEnQueue(0x48C3CE70)`(`0x00080607`)이 `tex=0x08C4DA60` (`w=512, h=256, bw=512, fmt=1, swz=1, 262144` bytes, FNV-1a 해시 `0x4F587C8C23DE34A8`, `rgba0=0xFFFFFFFF`, `tfunc=0`, `blend=1`)을 `fb=0x04044000`에 `(0,0)-(479,271)`로 그리고 `sceGeDrawSync(0)` → `sceDisplayWaitVblankStartCB()` → `sceDisplaySetFrameBuf(0x04044000, 512, 1, 0)`으로 표시한다.
  2. 곡 로딩 구간(약 80 vblank): `sceIoReadAsync`는 `0x0892E798..0x0896E798`, `0x09582AE0..0x095B8470`에만 읽었고 `sceDmacMemcpy` 호출은 0건이었다. 같은 메인 스레드에서 게스트 CPU 코드(`all.mp` 압축 해제·게스트 메모리 관리자 할당/해제)가 `0x08C4DA60` 영역을 새 데이터(해시 `0xDD0E554111BB02E2`)로 덮어썼다.
  3. 전환 첫 프레임(노이즈 프레임): 로딩 완료 후 게스트 메인 스레드가 **새 디스플레이 리스트**(`0x00080608`)를 제출하여, `fb=0x04000000`을 `(0,0)-(480,272)` `rgba0=0x00000000`으로 지운 뒤 덮어써진 `tex=0x08C4DA60`(`512x256, fmt=1, hash=0xDD0E554111BB02E2, rgba0=0xFFFFFFFF`)을 `(0,0)-(479,271)`에 다시 그렸다. 이어 `sceGeDrawSync(0)` → `sceDisplayWaitVblankStartCB()` → `sceDisplaySetFrameBuf(0x04000000, 512, 1, 0)`이 호출되어 한 vblank 동안 실제 표시 버퍼로 출력된 뒤, 다음 프레임(`fb=0x04044000`)부터 정상 플레이 화면(`0x09582FB0`)으로 넘어갔다.
* **판단 및 조치**:
  * 수정 전에는 GL의 `HashGuestRange`가 User RAM 텍스처 해시를 `0`으로 반환해 옛 표지 캐시가 재사용되면서 이 현상이 가려졌으나, 수정 후 GL이 `sw`와 동일하게 실제 게스트 RAM을 읽게 되면서 게임 자체가 덮어쓴 `0x08C4DA60` 버퍼를 한 프레임 더 그리는 원래 동작이 그대로 드러난 것으로 확인되었다.
  * 스레드 경합이나 HLE 비동기 타이밍 오류가 아닌 단일 메인 스레드의 순차 실행이므로 코드를 변경하지 않고 근거와 함께 리뷰어/사용자에게 질의로 올린다(임시 `[I043_*]` 진단 로그는 모두 제거).

# 2026-11-17 Work Log: Second Song Jacket Reuse Fix (#43)

Design: [20261117-i043-song-jacket.md](../design/20261117-i043-song-jacket.md)
Work order: [20261117-i043-song-jacket.md](../work-orders/20261117-i043-song-jacket.md)

## 1. Reproduction & Renderer Comparison

* Input script (`--max-vblanks 3900`): selects DISC 01 (`바람에게 부탁해`), transitions through `GAME OVER` back to `1st.STAGE` song select, and presses `RIGHT` + `CIRCLE` to start DISC 02 (`Luv Flow`) through its eyecatch/jacket screen.
* **Renderer comparison**:
  * `--renderer sw`: first song jacket is right, and second song eyecatch (`frame_1452.bmp`) correctly shows **`Luv Flow`**.
  * `--renderer gl` (before fix): the zoomed disc in song select shows `Luv Flow`, but the full-screen eyecatch/jacket after song select (`frame_2478.bmp`) still shows the first song **`바람에게 부탁해`**.
  * Conclusion: the defect is in the **GL texture cache**, not image reloading or decoding.

## 2. Root Cause & Evidence

* Logging large texture uploads (`st.tex_w >= 256 && st.tex_h >= 256`) in `ResolveTextureLocked()` (`third_party/repsp/src/gpu/gl_backend.cpp`) revealed that every non-CLUT texture (`fmt=1` ABGR1555, `fmt=2` ABGR4444, `fmt=3` ABGR8888) in User RAM (`0x08000000..0x0A000000`) had `content_hash = 0x0000000000000000`.
  * Examples: `addr=0x08C4DA60 w=512 h=256 bw=512 fmt=1 swz=1 bytes=262144 hash=0x0000000000000000`, `addr=0x08DC1F50 w=512 h=256 bw=512 fmt=2 swz=1 bytes=262144 hash=0x0000000000000000`, `addr=0x09219110 w=512 h=256 bw=512 fmt=3 swz=1 bytes=524288 hash=0x0000000000000000`.
* **Root cause (`HashGuestRange` in `gl_backend.cpp`)**:
  * `if (addr >= runtime::GuestMemory::kVramAddress)` lacked an upper bound, so **every User RAM address (`0x08xxxxxx`–`0x09xxxxxx`)** failed `off > kVramSize` and returned `0`.
  * Only CLUT textures (`fmt=5`, etc.) subsequently hashed the CLUT table to get a non-zero `content_hash`, whereas all non-CLUT textures (including the song eyecatch) were cached with `content_hash == 0` and collided (`0 == 0`) when overwritten at the same address, dimensions, and format.

## 3. Fix & Synthetic Probe

* **`HashGuestRange` fix (`third_party/repsp/src/gpu/gl_backend.cpp`)**: Replaced the broken VRAM check with `GuestMemory::IsValidAddress(addr, size)` (covering Scratchpad/VRAM/Kernel/User RAM and mirror folding) before hashing `Translate(addr)` with FNV-1a.
* **Synthetic probe (`third_party/repsp/tools/gl_probe/main.cpp`)**: Draws a 16×16 `ABGR8888` (`fmt=3`) red (`0xFF0000FF`) texture in User RAM (`0x08900000`), overwrites the exact same address with green (`0xFF00FF00`), redraws with identical `addr`/`w`/`h`/`bw`/`fmt`, and asserts the rendered pixel updates to green (fails before fix, passes after).

## 4. Measurements & Verification

* **Two-song `gl` frame dump (after fix)**: `frame_2323.bmp` correctly shows **`Luv Flow`** (`tex_uploads`: `84` → `121`).
* **3 Release runs (`--headless --renderer gl --max-vblanks 2400`)**:
  * Run #1: `Exit code: 0`, `Dispatches: 0`, `Present: 1924 frames (interval mean=20.81 ms)` (`draws=22389, tex_uploads=90, tex_hits=52948`)
  * Run #2: `Exit code: 0`, `Dispatches: 0`, `Present: 1923 frames (interval mean=20.81 ms)` (`draws=22371, tex_uploads=90, tex_hits=52881`)
  * Run #3: `Exit code: 0`, `Dispatches: 0`, `Present: 1926 frames (interval mean=20.79 ms)` (`draws=22449, tex_uploads=88, tex_hits=53025`)
  * Presentation intervals (`20.79–20.81 ms`) match the prior baseline with no regression.
* **Builds & CTest**:
  * Win64 Ninja Release **35/35 passed** (`6.69 s`), Win64 Ninja Debug **35/35 passed** (`8.37 s`).
  * Visual Studio 18 2026 generator build/CTest and Linux x64 (WSL) status are recorded separately.

## 5. Follow-up Investigation: Eyecatch → Gameplay Transition Noise Frame (#43b)

* **Symptom & Renderer Comparison (`--renderer sw` vs `--renderer gl`)**:
  * Right at the transition from the song eyecatch (jacket) screen to gameplay, a garbled frame appears in which a gameplay UI texture atlas (`COOL`/`GOOD`/`MAX`/`BREAK`, etc.) is stretched across the entire screen in the wrong pixel format.
  * Capturing the two-song input script shows the **exact same noise frame on both `--renderer sw` (`frame_1453.bmp`) and `--renderer gl` (`frame_2324.bmp`)**, ruling out a GL-only bug.
* **Trace Evidence (`GeInterpreter`, `hle_display`, `iofilemgr`, `hle_dmac`, `REPSP_HLE_TRACE`)**:
  1. Eyecatch draw: `sceGeListEnQueue(0x48C3CE70)` (`0x00080607`) draws `tex=0x08C4DA60` (`w=512, h=256, bw=512, fmt=1, swz=1, 262144` bytes, FNV-1a hash `0x4F587C8C23DE34A8`, `rgba0=0xFFFFFFFF`, `tfunc=0`, `blend=1`) over `(0,0)-(479,271)` into `fb=0x04044000`, followed by `sceGeDrawSync(0)` → `sceDisplayWaitVblankStartCB()` → `sceDisplaySetFrameBuf(0x04044000, 512, 1, 0)`.
  2. Song loading (~80 vblanks): `sceIoReadAsync` only writes into `0x0892E798..0x0896E798` and `0x09582AE0..0x095B8470`, and `sceDmacMemcpy` is called 0 times. Guest CPU code on the same main thread (asset decompression and the guest memory manager) overwrites `0x08C4DA60` with new data (`hash=0xDD0E554111BB02E2`).
  3. First transition frame (noise frame): Once loading finishes, the guest main thread enqueues a **new display list** (`0x00080608`) that clears `fb=0x04000000` over `(0,0)-(480,272)` (`rgba0=0x00000000`), then draws the overwritten `tex=0x08C4DA60` (`512x256, fmt=1, hash=0xDD0E554111BB02E2, rgba0=0xFFFFFFFF`) over `(0,0)-(479,271)`, and calls `sceGeDrawSync(0)` → `sceDisplayWaitVblankStartCB()` → `sceDisplaySetFrameBuf(0x04000000, 512, 1, 0)` before switching to gameplay (`0x09582FB0`) on `fb=0x04044000` on the next frame.
* **Conclusion & Action**:
  * Before the #43 fix, `HashGuestRange` returned `0` for User RAM textures, so GL accidentally kept reusing the cached old jacket texture and masked this behavior. Once GL reads actual guest RAM like `sw`, both renderers faithfully show the game's own sequential draw of the already-overwritten `0x08C4DA60` buffer.
  * Because this is sequential main-thread guest logic (not a thread race or HLE async timing bug), no code workaround was added; all temporary `[I043_*]` logs were removed and the evidence is escalated as a question.
