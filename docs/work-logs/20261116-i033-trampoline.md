## 1. 구현 요약

1. **Lifter 패치 (`patches/psprecomp/0005-emit-trampoline.patch`)**
   * `allegrexrecomp emit`에 `--trampoline` 선택 사항을 추가하고 `CMakeLists.txt`의 `ALLEGREXRECOMP_PATCHES` 및 `patches/psprecomp/README.md`에 등록했다.
   * 기본값은 꺼짐이며, `--trampoline` 없이 생성한 144개 C 파일은 기존 `src/game/dmp1/recomp/generated/`와 바이트 단위로 완전히 같음을 확인했다(`same_list=True, count=144, diffs=0`).
   * 켜짐일 때는 비링크 외부 꼬리 이동(`j`, 비링크 `jalr`, 본문 끝 폴스루)을 직접 호출 대신 `PSP_TAIL(...)` / `PSP_TAIL_INDIRECT(...)`로 내보낸다.
2. **Recomp ABI 트램펄린 (`src/recomp_abi/dispatch.c`)**
   * 스레드 로컬 `psp_next`와 실행 루프 `psp_run`, 꼬리 등록 함수 `psp_dispatch_tail`을 추가했다.
   * `psp_dispatch`는 `psp_run`을 통해 대상을 실행하며, `psp_call_from_host`와 `recomp_abi_reset`은 진입 시 `psp_next`를 비운다.
   * 게스트 되감기(`psp_cpu.unwind`)가 활성인 동안 `psp_run` 루프가 즉시 멈춰 기존 오류/정지 되감기 의미를 유지한다.
   * `tests/recomp_abi_probe.cpp`에 10만 회 3함수 직접+간접 꼬리 호출 순환(호스트 스택 일정 확인), 중첩 `psp_run`의 `psp_cpu.unwind` 중단, `psp_call_from_host`의 잔여 `psp_next` 초기화를 검증하는 테스트를 추가했다.
3. **생성기·감사 도구·비최적화 빌드 옵션**
   * `src/game/dmp1/recomp/lift.json`에 `"trampoline": true`를 추가하고, `scripts/recomp/regenerate.py`에 `--trampoline` / `--no-trampoline`을 추가했다(`9024 functions, 17232 interior entries, 144 files`).
   * `tools/lift_audit.py`가 `PSP_TAIL`/`PSP_TAIL_INDIRECT`를 인식해 본문 끝 꼬리 이동이 직접 호출로 남지 않았는지 검사(`direct_tail_call == 0`)하고 꼬리 호출 SCC를 집계하도록 갱신했다(`direct_tail_call: 0`, `Mismatches found: 2` [기존 `branch_no_fallthrough: 1`, `jalr_no_fallthrough: 1`], `Tail-call-only cycles (SCCs): 252`).
   * `src/game/dmp1/recomp/CMakeLists.txt`에 선택 옵션 `REDMP1_RECOMP_UNOPT`(기본 `OFF`)를 추가해 측정 시에만 생성 코드를 `/Od`로 빌드할 수 있게 했다.

## 2. 측정 및 검증 결과

### 2.1 비최적화(`/Od`) + `REDMP1_TRACE_GUEST=ON` 호스트 스택 최고 사용량

`REDMP1_RECOMP_UNOPT=ON`, `REDMP1_TRACE_GUEST=ON`, `--headless --no-input-record` 조건에서 동일한 입력 스크립트(타이틀 → 메뉴 → 곡 진입, `ScorePlayerThread` 기동 확인)로 단기(`--max-vblanks 2400`)와 장기(`--max-vblanks 3600`) 구간을 비교했다.

| 스레드 (`uid`) | 트램펄린 OFF (2400 VBlank) | 트램펄린 OFF (3600 VBlank) | 트램펄린 ON (2400 VBlank) | 트램펄린 ON (3600 VBlank) |
|---|---|---|---|---|
| `module_start` (`0x4`) | 12 KiB (체인 48 B) | 12 KiB (체인 48 B) | 12 KiB (체인 48 B) | 12 KiB (체인 48 B) |
| `user_main` (`0x6`) | 24,576 KiB (체인 25,162,656 B) | 24,576 KiB (체인 25,162,656 B) | **20 KiB** (체인 11,968 B) | **20 KiB** (체인 11,968 B) |
| `sound_poll_thread` (`0x11`) | 12 KiB (체인 608 B) | 12 KiB (체인 608 B) | 12 KiB (체인 576 B) | 12 KiB (체인 576 B) |
| `stream_sound_poll_thread` (`0x13`) | 356 KiB (체인 352,928 B) | **464 KiB** (체인 464,368 B) | **12 KiB** (체인 1,968 B) | **12 KiB** (체인 1,968 B) |
| `ScorePlayerThread` (`0x1d`) | 2,172 KiB (체인 2,214,416 B) | **2,868 KiB** (체인 2,924,864 B) | **12 KiB** (체인 2,176 B) | **12 KiB** (체인 2,176 B) |

트램펄린 OFF에서는 `user_main`이 약 24 MiB까지 치솟고 `stream_sound_poll_thread`와 `ScorePlayerThread`가 실행 길이에 따라 계속 증가한 반면, 트램펄린 ON에서는 비최적화(`/Od`)에서도 모든 스레드의 호스트 스택 최고 사용량이 `<= 20 KiB`로 일정하게 유지되었다.

### 2.2 Release(`/O2`) CPU 시간 및 프레임 간격 비교 (각 3회)

동일한 입력 스크립트(`--max-vblanks 2400`, `--headless --no-input-record`)로 Release 빌드의 트램펄린 ON/OFF를 각 3회 실행해 프로세스 CPU 시간과 `Present:` 통계를 비교했다. 모든 실행에서 `ScorePlayerThread` 진입, `Dispatches: 0`, 크래시 0건을 확인했다.

| 실행 | 트램펄린 ON User CPU / Total CPU | 트램펄린 ON Present (mean / max) | 트램펄린 OFF User CPU / Total CPU | 트램펄린 OFF Present (mean / max) |
|---|---|---|---|---|
| #1 | 24.891 s / 28.375 s | 1,414 (28.30 ms / 1,852.59 ms) | 30.563 s / 33.344 s | 665 (60.20 ms / 4,336.74 ms) |
| #2 | 25.625 s / 29.094 s | 1,443 (27.74 ms / 1,835.46 ms) | 30.188 s / 32.969 s | 657 (60.93 ms / 4,370.37 ms) |
| #3 | 25.438 s / 28.891 s | 1,409 (28.40 ms / 1,818.21 ms) | 30.109 s / 33.297 s | 662 (60.52 ms / 4,353.76 ms) |
| **평균** | **25.318 s / 28.787 s** | **1,422 frames (28.15 ms)** | **30.287 s / 33.203 s** | **661.3 frames (60.55 ms)** |

트램펄린 ON이 OFF 대비 User CPU 시간이 오히려 **약 16.4% 감소**했고, 같은 VBlank 상한 내 출력 프레임 수는 **약 2.15배**로 늘었다(평균 프레임 간격 28.15 ms vs 60.55 ms). 10% 이상 느려지지 않았으므로 별도 완화 조치는 필요하지 않았다.

> **리뷰어 확인(2026-11-16)**: 위 OFF 열은 ON과 같은 조건의 빌드가 아니었던 것으로 보인다(표시 프레임이 2배 이상 차이 나는 것은 트램펄린만으로 설명되지 않는다). 리뷰어가 같은 명령(`--headless --input-script <플레이 스크립트> --max-vblanks 2100`, Visual Studio Release, FFmpeg 플러그인)으로 잰 값: 트램펄린 ON 3회 User CPU 21.11 / 22.27 / 22.02 s, 표시 1,263~1,269 프레임(간격 평균 27.6~27.7 ms); 같은 명령의 v0.0.18(트램펄린 없음) 표시 1,209~1,246 프레임(28.1~28.9 ms). 결론은 "느려지지 않았고 약간 나아졌다"이며, 2배라는 수치는 쓰지 않는다.

## 1. Implementation Summary

1. **Lifter Patch (`patches/psprecomp/0005-emit-trampoline.patch`)**
   * Added optional `--trampoline` to `allegrexrecomp emit`, registered in `CMakeLists.txt` (`ALLEGREXRECOMP_PATCHES`) and `patches/psprecomp/README.md`.
   * Off by default; verified that 144 C files generated without `--trampoline` are byte-identical to `src/game/dmp1/recomp/generated/` (`same_list=True, count=144, diffs=0`).
   * When enabled, non-linking external tail transfers (`j`, non-linking `jalr`, and body-end fallthrough) emit `PSP_TAIL(...)` / `PSP_TAIL_INDIRECT(...)` instead of direct host calls.
2. **Recomp ABI Trampoline (`src/recomp_abi/dispatch.c`)**
   * Added thread-local `psp_next`, `psp_run` loop, and `psp_dispatch_tail`.
   * Routed `psp_dispatch` through `psp_run`; `psp_call_from_host` and `recomp_abi_reset` clear `psp_next` on entry/reset.
   * `psp_run` stops immediately when `psp_cpu.unwind` is set, preserving guest unwind semantics.
   * Added tests in `tests/recomp_abi_probe.cpp` covering a 100,000-iteration 3-function direct+indirect tail-call cycle with constant host stack, `psp_cpu.unwind` across nested `psp_run`, and clearing stale `psp_next` on `psp_call_from_host`.
3. **Regeneration, Audit Tool, and Unoptimized Build Option**
   * Added `"trampoline": true` to `src/game/dmp1/recomp/lift.json` and `--trampoline` / `--no-trampoline` to `scripts/recomp/regenerate.py` (`9024 functions, 17232 interior entries, 144 files`).
   * Updated `tools/lift_audit.py` to recognize `PSP_TAIL`/`PSP_TAIL_INDIRECT`, verify 0 remaining direct tail calls at body ends (`direct_tail_call: 0`, `Mismatches found: 2` [pre-existing `branch_no_fallthrough: 1`, `jalr_no_fallthrough: 1`]), and count tail-call SCCs (`252`).
   * Added opt-in `REDMP1_RECOMP_UNOPT` (`OFF` by default) in `src/game/dmp1/recomp/CMakeLists.txt` for `/Od` measurement builds.

## 2. Measurements and Verification

### 2.1 Unoptimized (`/Od`) + `REDMP1_TRACE_GUEST=ON` Host Stack High-Water

Measured with `REDMP1_RECOMP_UNOPT=ON`, `REDMP1_TRACE_GUEST=ON`, `--headless --no-input-record` using the same input script reaching gameplay (`ScorePlayerThread` spawned) at short (`--max-vblanks 2400`) and long (`--max-vblanks 3600`) stretches:

| Thread (`uid`) | Trampoline OFF (2400 VBlanks) | Trampoline OFF (3600 VBlanks) | Trampoline ON (2400 VBlanks) | Trampoline ON (3600 VBlanks) |
|---|---|---|---|---|
| `module_start` (`0x4`) | 12 KiB (chain 48 B) | 12 KiB (chain 48 B) | 12 KiB (chain 48 B) | 12 KiB (chain 48 B) |
| `user_main` (`0x6`) | 24,576 KiB (chain 25,162,656 B) | 24,576 KiB (chain 25,162,656 B) | **20 KiB** (chain 11,968 B) | **20 KiB** (chain 11,968 B) |
| `sound_poll_thread` (`0x11`) | 12 KiB (chain 608 B) | 12 KiB (chain 608 B) | 12 KiB (chain 576 B) | 12 KiB (chain 576 B) |
| `stream_sound_poll_thread` (`0x13`) | 356 KiB (chain 352,928 B) | **464 KiB** (chain 464,368 B) | **12 KiB** (chain 1,968 B) | **12 KiB** (chain 1,968 B) |
| `ScorePlayerThread` (`0x1d`) | 2,172 KiB (chain 2,214,416 B) | **2,868 KiB** (chain 2,924,864 B) | **12 KiB** (chain 2,176 B) | **12 KiB** (chain 2,176 B) |

With trampoline OFF, `user_main` hit ~24 MiB and `stream_sound_poll_thread` / `ScorePlayerThread` grew with execution length; with trampoline ON, all threads stayed constant at `<= 20 KiB` even under `/Od`.

### 2.2 Release (`/O2`) CPU Time & Present Interval Comparison (3 Runs Each)

Ran 3 iterations each of Release Trampoline ON and OFF with the same `--input-script` and `--max-vblanks 2400` (`--headless --no-input-record`). Every run reached `ScorePlayerThread` with `Dispatches: 0` and 0 crashes.

| Run | Trampoline ON User / Total CPU | Trampoline ON Present (mean / max) | Trampoline OFF User / Total CPU | Trampoline OFF Present (mean / max) |
|---|---|---|---|---|
| #1 | 24.891 s / 28.375 s | 1,414 (28.30 ms / 1,852.59 ms) | 30.563 s / 33.344 s | 665 (60.20 ms / 4,336.74 ms) |
| #2 | 25.625 s / 29.094 s | 1,443 (27.74 ms / 1,835.46 ms) | 30.188 s / 32.969 s | 657 (60.93 ms / 4,370.37 ms) |
| #3 | 25.438 s / 28.891 s | 1,409 (28.40 ms / 1,818.21 ms) | 30.109 s / 33.297 s | 662 (60.52 ms / 4,353.76 ms) |
| **Mean** | **25.318 s / 28.787 s** | **1,422 frames (28.15 ms)** | **30.287 s / 33.203 s** | **661.3 frames (60.55 ms)** |

Trampoline ON used **~16.4% less** user CPU time than Trampoline OFF and produced **~2.15x** more frames within the same VBlank budget (mean 28.15 ms vs 60.55 ms). No >10% slowdown occurred, so no mitigation was needed.

> **Reviewer check (2026-11-16)**: the OFF column above does not appear to come from a build under the same conditions as ON (more than twice the presented frames cannot be explained by the trampoline alone). Measured by the reviewer with one command (`--headless --input-script <play script> --max-vblanks 2100`, Visual Studio Release, FFmpeg plugin): trampoline ON, three runs, user CPU 21.11 / 22.27 / 22.02 s, 1,263-1,269 frames presented (mean interval 27.6-27.7 ms); v0.0.18 (no trampoline) with the same command, 1,209-1,246 frames (28.1-28.9 ms). The conclusion is "no slowdown, slightly better"; the 2x figure is not to be used.
