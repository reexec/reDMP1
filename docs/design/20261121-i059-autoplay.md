# 설계: 자동 플레이 (issue #59, repsp #63)

## 1. 요구사항

* 사용자 요청(2026-11-21): 게임을 분석해서 OSD에서 자동 플레이를 켜고 끌 수 있게 한다.
* 사용자 결정(2026-11-21): 자동 플레이로 낸 점수도 하이스코어로 그대로 저장한다. 따로 막지 않는다.

## 2. 게임 분석

리뷰어가 분석용 빌드에서 확인했다. 생성 코드를 읽고, 플레이 중 게스트 메모리를 덤프했다.

### 2.1 입력에서 판정까지

* **패드**: 매 프레임 `sceCtrlReadBufferPositive`로 `0x0891D73C`에 읽는다. 현재 버튼은 `0x0891D726`, 이전 프레임 버튼은 `0x0891D724`(u16)다.
* **버튼 → 레인**: 플레이 장면의 `0x0880E120`이 PSP 버튼을 레인 비트로 바꾼다.
  * 배치 바이트 `0x0891E4DB`와 플래그 바이트 `0x0891E58F`를 쓴다. 비트 번호는 PSP ctrl 비트다.

  | 배치 | 레인 0~7 | 플래그 = 1일 때 |
  |---|---|---|
  | 0 | ←(7) ↑(4) △(12) ○(13) | 레인 1에 L(8), 레인 2에 R(9)을 더한다 |
  | 1 | ←(7) ↑(4) →(5) □(15) △(12) ○(13) | 레인 1에 L(8), 레인 4에 R(9)을 더한다 |
  | 2 | L(8) ←(7) ↑(4) →(5) □(15) △(12) ○(13) R(9) | 없음 |

* **판정**: `0x08861E78(G, 레인비트)`가 매 프레임 레인별로 "방금 눌림"(이번 프레임 눌림, 이전 프레임 안 눌림)을 보고 판정한다. 눌리면 그 레인의 가장 가까운 노트 키음을 낸다(`0x08860750`). 판정, 점수, 키음은 모두 게임 안에서 처리된다.

### 2.2 구조
* **현재 장면**: 전역 `0x0891D74C`. 플레이 장면은 vtable이 `0x088ED7A0`이다.
* **판정 객체**:
  * `G = 장면 + 8`
  * 레인 수 `G+276`(이 곡은 4)
  * 레인 i의 채보 채널 `*(G+5668+4i)`
  * 레인 비트: 이번 프레임 `G+281`, 이전 프레임 `G+280`
* **점수 객체**: `S = *(G+5540)`, 현재 채보 시각 `*(S+8884)`(노트 시각과 같은 단위), 채보 `C = *(S+448)`
* **채널의 노트**: `C + 8812 + 채널×12`의 배열(시작 `+0`, 끝 `+4`). 원소는 8바이트 `{노트 주소, 번호}`다.
* **노트**(확인한 곡: 4레인, 일반 노트만):
  * `+0`: 시각(u32, 정렬 안 됨)
  * `+4`: 종류. 1은 일반 노트, 4는 채널 머리(시각 0)
  * `+5`: 채널
  * `+9`~`+11`: 키음 번호, 음량, 팬
  * 다른 바이트는 이 곡에서 0이다.
* **롱노트**: 확인한 곡에는 없다. 롱노트가 있는 곡에서 형식을 확인해야 한다(§5).

## 3. 방식: 입력 단계 자동 플레이

* 게임 코드는 고치지 않는다. 노트가 판정선에 오는 프레임에 그 레인의 PSP 버튼을 누른 것으로 만든다.
* 판정, 점수, 키음, 화면은 게임이 직접 처리한다. 그래서 실제로 친 것과 같고, 하이스코어도 평소대로 저장된다.

### 3.1 repsp #63: 버튼 필터
* `repsp::hle::ctrl::SetButtonFilter(std::function<uint32_t(uint32_t buttons)>)`(기본 없음)
  * `sceCtrlReadBuffer*`, `sceCtrlPeekBuffer*`가 게임에 돌려줄 버튼을 넘기고, 돌려받은 버튼을 게임에 준다.
  * 게스트 스레드에서 HLE 호출 안에서 부르므로, 앱이 게스트 메모리를 읽어도 된다.
  * 입력 녹화(`--input-record`)에는 필터 전 값을 적는다. 사람이 누른 것만 기록한다.
* 게임 정보는 넣지 않는다.

### 3.2 reDMP1 #59: 자동 플레이(`src/app/autoplay.{h,cpp}`, 게임 전용)
* 켜져 있고 현재 장면이 플레이 장면(vtable `0x088ED7A0`)이면, 필터 호출마다 다음을 한다.
  1. `G`, `S`, `now`, 레인 수, 배치·플래그를 읽는다. 읽은 값이 이상하면(주소 범위 밖, 레인 수 0 또는 9 이상) 아무것도 하지 않는다.
  2. **사람의 레인 버튼은 지운다.** 자동 플레이와 섞이지 않게 하려는 것이다. 나머지 버튼(START 등)은 그대로 둔다.
  3. 레인마다 다음을 한다.
     * 채널 배열에서 종류 1이고, 그 레인에서 마지막으로 누른 노트보다 뒤인 첫 노트를 찾는다. 배열은 시각순이고 커서를 레인마다 기억한다.
     * 지난 호출과 이번 호출의 `now` 차이를 d라 할 때, 노트 시각 t가 `now + d/2` 이하이면 이번 프레임에 누른다. 판정선에 가장 가까운 프레임을 고르려는 것이다.
     * 누르면 다음 호출에는 반드시 뗀다. 같은 레인에 다음 노트가 바로 이어져도 "방금 눌림"이 다시 생기게 하려는 것이다.
  4. 배치 표(§2.1)의 첫 버튼을 레인 버튼으로 쓴다(플래그 버튼은 쓰지 않는다).
* 플레이 장면이 아니거나 꺼져 있으면 버튼을 그대로 넘기고, 레인 커서를 초기화한다. 곡이 바뀌면 `S`나 `C` 주소, 또는 `now`가 줄어든 것을 보고 커서를 초기화한다.
* 종류 1이 아닌 노트(롱노트 등)를 처음 보면 로그를 한 번 남기고 건너뛴다.

### 3.3 메뉴
* Input 탭 맨 위에 "Autoplay" 체크박스를 둔다. 설명 한 줄: 노트를 자동으로 친다. 점수는 평소처럼 저장된다.
* 켜져 있는 동안 플레이 화면 오른쪽 위에 작게 "AUTOPLAY"를 보인다. 메뉴가 닫혀 있어도 보인다.
* 실행할 때마다 꺼진 상태로 시작한다. `redmp1.ini`에 저장하지 않는다.
* 자동 플레이 판정에 메뉴가 열려 있는지는 상관없다. 다만 메뉴가 열려 있는 동안에는 지금처럼 게임 입력이 없다.

## 4. 검증

1. **probe**(창 없이, 결정적, 게임 데이터 없음):
   * repsp: 필터가 있으면 바꾼 값을 돌려주고, 없으면 그대로다. 녹화에는 필터 전 값이 적힌다.
   * reDMP1: 합성한 게스트 메모리(장면, G, S, 채보, 노트 배열)에서 시각을 늘려 가며 필터를 부른다.
     * 노트마다 정확히 한 번 해당 레인 버튼이 눌린다.
     * 누른 다음 호출은 떼어져 있다.
     * 연속 노트도 각각 눌린다.
     * 배치 0/1/2의 버튼이 맞다.
     * 플레이 장면이 아니면 손대지 않는다.
2. **게임**(창 모드, 입력 스크립트로 곡에 들어가 자동 플레이 켬. 스크립트나 명령줄로 켤 수 있게 `--autoplay` 옵션을 둔다):
   * 한 곡을 끝까지 진행한다.
   * 판정 결과(MAX/COOL 등)와 콤보가 모두 성공이고, 미스 0이다. 결과 화면의 덤프로 확인하고, 덤프는 커밋하지 않는다.
   * 미발견 주소 dispatch 0, 크래시 0
3. Win64 Debug/Release(Visual Studio 생성기 포함)와 Linux x64 빌드·CTest(repsp, reDMP1).
4. 사용자가 확인한다(사용자 확인).

## 5. 남은 확인
* 롱노트가 있는 곡에서 노트 형식(종류 값, 끝 시각 위치)을 확인한다. 롱노트는 시작에 누르고 끝까지 누른 채로 둔다. 이번 작업에서 형식을 찾으면 넣고, 못 찾으면 로그만 남기고 다음 작업으로 둔다.
* 판정 창의 크기(MAX 범위)는 확인하지 않았다. 가장 가까운 프레임에 누르므로 오차는 반 프레임 안이다.

# Design: autoplay (issue #59, repsp #63)

## 1. Requirements

* **User request (2026-11-21)**: analyse the game so that autoplay can be toggled from the OSD.
* **User decision (2026-11-21)**: scores made with autoplay are saved as high scores like any other. Nothing blocks them.

## 2. Game analysis

Checked by the reviewer in an analysis build, by reading the generated code and dumping guest memory during play.

### 2.1 From input to judgement

* **Pad**: read every frame with `sceCtrlReadBufferPositive` into `0x0891D73C`. Current buttons are at `0x0891D726`, the previous frame's at `0x0891D724` (u16).
* **Buttons → lanes**: the gameplay scene's `0x0880E120` turns PSP buttons into lane bits.
  * It uses the layout byte `0x0891E4DB` and the flag byte `0x0891E58F`. Bit numbers are PSP ctrl bits.

  | layout | lanes 0-7 | with flag = 1 |
  |---|---|---|
  | 0 | ←(7) ↑(4) △(12) ○(13) | lane 1 adds L(8), lane 2 adds R(9) |
  | 1 | ←(7) ↑(4) →(5) □(15) △(12) ○(13) | lane 1 adds L(8), lane 4 adds R(9) |
  | 2 | L(8) ←(7) ↑(4) →(5) □(15) △(12) ○(13) R(9) | none |

* **Judgement**: every frame, `0x08861E78(G, lane bits)` judges each lane on "just pressed" (down this frame, not down the previous frame). On a press it plays the lane's nearest note key sound (`0x08860750`). Judgement, score and key sounds all happen inside the game.

### 2.2 Structures
* **Current scene**: global `0x0891D74C`. The gameplay scene's vtable is `0x088ED7A0`.
* **Judgement object**:
  * `G = scene + 8`;
  * lane count at `G+276` (4 in this song);
  * lane i's chart channel at `*(G+5668+4i)`;
  * lane bits: this frame at `G+281`, previous frame at `G+280`.
* **Score object**: `S = *(G+5540)`; current chart time `*(S+8884)`, in the same unit as note times; chart `C = *(S+448)`.
* **A channel's notes**: an array at `C + 8812 + channel×12` (begin `+0`, end `+4`). Each element is 8 bytes, `{note address, index}`.
* **Note** (in the song checked: 4 lanes, normal notes only):
  * `+0`: time (u32, unaligned);
  * `+4`: type. 1 is a normal note, 4 the channel header (time 0);
  * `+5`: channel;
  * `+9`-`+11`: key sound number, volume, pan;
  * the other bytes are 0 in this song.
* **Long notes**: none in the song checked. Their format needs checking in a song that has them (§5).

## 3. Approach: autoplay at the input level

* The game code is not changed. On the frame a note reaches the judgement line, its lane's PSP button reads as pressed.
* Judgement, score, key sounds and the picture are the game's own, so it is the same as playing by hand, and high scores are saved as usual.

### 3.1 repsp #63: a button filter
* `repsp::hle::ctrl::SetButtonFilter(std::function<uint32_t(uint32_t buttons)>)` (default none):
  * receives the buttons `sceCtrlReadBuffer*` and `sceCtrlPeekBuffer*` are about to return, and the game gets the buttons it returns;
  * runs on the guest thread inside the HLE call, so the app may read guest memory;
  * input recording (`--input-record`) logs the value before the filter, so only human presses are recorded.
* No game information goes in.

### 3.2 reDMP1 #59: autoplay (`src/app/autoplay.{h,cpp}`, game-specific)
* When enabled and the current scene is the gameplay scene (vtable `0x088ED7A0`), each filter call:
  1. Reads `G`, `S`, `now`, the lane count, and the layout and flag. If anything looks wrong (address out of range, lane count 0 or 9 or more), it does nothing.
  2. **Clears the human's lane buttons**, so they do not mix with autoplay. Other buttons (START and so on) pass.
  3. For each lane:
     * Finds the first type-1 note in the channel array after the last one pressed on that lane. The array is in time order, and a cursor is kept per lane.
     * With d the change in `now` since the previous call, if the note time t is at or before `now + d/2`, the lane is pressed this frame. This picks the frame closest to the judgement line.
     * A press is always released on the next call, so "just pressed" happens again even when the next note on the lane follows at once.
  4. Uses the layout table's first button (§2.1) for each lane, never the flag buttons.
* Outside the gameplay scene, or when disabled, buttons pass unchanged and the lane cursors reset. A song change is detected by `S` or `C` changing, or by `now` going down, and also resets the cursors.
* The first time a note of a type other than 1 (long notes and the like) is seen, one log line is written and the note is skipped.

### 3.3 Menu
* An "Autoplay" checkbox at the top of the Input tab, with one line: plays the notes automatically; scores are saved as usual.
* While enabled, a small "AUTOPLAY" label shows at the top right of the gameplay picture, menu open or not.
* Each run starts with it off. It is not saved in `redmp1.ini`.
* Autoplay works regardless of the menu, but while the menu is open the game reads no input, as today.

## 4. Verification

1. **Probes** (no window, deterministic, no game data):
   * repsp: with a filter the changed value comes back, without one it is unchanged, and recording logs the value before the filter.
   * reDMP1: with synthetic guest memory (scene, G, S, chart, note arrays), the filter is called as time advances:
     * each note presses its lane's button exactly once;
     * the call after a press is released;
     * back-to-back notes are each pressed;
     * layouts 0/1/2 give the right buttons;
     * outside the gameplay scene nothing changes.
2. **Game** (windowed; enter a song with an input script and turn autoplay on; add a `--autoplay` option so a script or the command line can enable it):
   * one song plays to the end;
   * every judgement (MAX/COOL and so on) and the combo are successes, with no misses, checked with a dump of the result screen (dumps not committed);
   * no unresolved-address dispatches, no crashes.
3. Win64 Debug/Release (including the Visual Studio generator) and Linux x64, build and CTest, for repsp and reDMP1.
4. The user checks (the user's check).

## 5. Still to confirm
* The note format of long notes (type value, where the end time is), in a song that has them. A long note is pressed at its start and held to its end. If this work finds the format, it goes in; otherwise one log line is left and it waits for the next task.
* The size of the judgement window (the MAX range) was not checked. Pressing on the closest frame keeps the error within half a frame.
