# 설계: 동영상 — sceMpeg를 앱에 연결하고 첫 화면을 향해 진행 (issue #13)

## 1. 요구사항

* repsp의 sceMpeg HLE([repsp issue #13](https://github.com/reexec/repsp/issues/13))를 앱에 연결한다. 부팅이 멈추던 `sceMpegInit` 너머로 진행한다.
* issue #9·#11과 같은 방식으로, 이미 다루는 라이브러리 안에서는 계속 나아간다(§2).
* **사용자 결정(issue #13)**: 영상은 지금은 검은 프레임, 음성은 무음으로 디코딩한다. 디코더 선택은 나중에 정한다.
* 동영상 재생 경로와, 그 뒤에 게임이 그리는 것을 원본 게임의 사실로 `docs/analysis/`에 기록한다.

## 2. 진행 범위

* **이미 다루는 라이브러리**: 커널(ThreadMan, SysMem, IoFileMgr, ModuleMgr, LoadExec, Utils, Stdio, Kernel_Library, power, suspend, UMD), `sceGe_user`, `sceDisplay`, `sceCtrl`, `sceDmac`, `sceAudio`, `sceSasCore`, `sceAtrac3plus`, `sceMpeg`.
* 정지가 이 라이브러리 안의 미구현 함수나 결함(미구현 GE 명령·SIGNAL 동작, 그리지 않는 primitive, 지원하지 않는 텍스처 형식 포함)이면, repsp submodule 브랜치에서 구현하거나 고치고 다시 실행한다. 추가한 함수는 probe로 검사하고, 커밋을 작업 로그에 적는다.
* 정지가 `sceUtility`의 호출이면 거기서 멈추고 기록한다.
* 설계 판단이 필요한 결함(스케줄러 의미 변경, 계약 변경, 디코더 문제 등)은 고치지 말고 작업 로그의 질문으로 올린다.
* 정지 없이 계속 도는 상태(동영상 재생 중, 타이틀 화면의 입력 대기 등)에서는 `--max-vblanks`로 끝내고 그 시점의 상태를 보고한다. 동영상이 끝난 뒤의 화면까지 보려면 한도를 영상 길이보다 길게 잡는다.
* 동영상을 건너뛰는 입력이 필요하면, 정해진 vblank에 버튼을 누르는 스크립트 입력을 앱 옵션으로 더한다(repsp `hle::ctrl::SetInputSource`). 형식은 `--input-script <file>`이고, 각 줄은 `<vblank> <버튼 이름들>`이다. 스크립트 파일은 저장소에 넣지 않는다.

## 3. 기록

* `docs/analysis/video.md`(새 파일): 동영상을 재생하는 코드 경로(스레드, 호출 순서), 링버퍼 크기(pack 수), 등록하는 스트림, 디코딩 루프와 속도를 맞추는 방식, 디코딩한 프레임을 화면에 내는 방식(GE 텍스처인지 프레임버퍼 직접 쓰기인지, 픽셀 형식), PSMF 헤더의 값(해상도, 길이, 스트림 구성), 원본 디스크 안에서 동영상 데이터가 오는 위치.
* `docs/analysis/first-frame.md`에 이어서: 정지 또는 한도까지의 HLE 순서, 그린 것이 있으면 리스트·primitive 통계, 쓴 텍스처 형식, 화면 내용의 글 서술(이미지는 저장소에 넣지 않는다), 다음 정지 NID와 이름.
* 원본 게임의 사실만 적는다. 사용자 덤프의 위치나 이름은 적지 않는다.

## 4. 이번 task의 검증

1. 로컬: `redmp1 roms --headless`가 `sceUtility`의 미구현 NID에서 정지 분류 (a)로 멈추거나, vblank 한도 (e)로 끝난다. 디스패치 미스, 교착이 없다.
2. 로컬: 프레임이 표시됐으면 프레임 덤프를 남기고 위치를 작업 로그에 적는다(리뷰어가 확인; 덤프는 커밋하지 않는다). 덤프가 많아지지 않게 `REPSP_FRAME_DUMP_LIMIT`를 쓰고, 내용이 바뀌는 지점의 프레임을 고른다.
3. 로컬: 3회 실행을 비교한다. 오디오·vblank 대기가 호스트 시각에 묶이므로 스레드 사이의 호출 순서가 달라질 수 있다. 다르면 원인을 분석해 기록한다.
4. CTest `app_boot`를 새 종료 지점으로 갱신한다. 실행 시간이 길어지면 CTest에는 짧은 한도를 쓴다.
5. Win64 Debug/Release와 Linux x64 빌드·CTest, CI 통과. 게임 데이터가 없는 구성(`REDMP1_HAVE_RECOMP=0`)도 경고 없이 빌드된다.

# Design: video — wiring sceMpeg into the app and running on toward the first picture (issue #13)

## 1. Requirements

Wire repsp's sceMpeg HLE ([repsp issue #13](https://github.com/reexec/repsp/issues/13)) into the app and run past `sceMpegInit`, where the boot stopped. As in issues #9 and #11, the run keeps going inside the libraries already covered (§2). **User decision (issue #13)**: video decodes to black frames and audio to silence for now; the decoders are chosen later. The movie playback path and whatever the game draws after it are recorded in `docs/analysis/` as facts about the original game.

## 2. How far to go

Libraries already covered: the kernel (ThreadMan, SysMem, IoFileMgr, ModuleMgr, LoadExec, Utils, Stdio, Kernel_Library, power, suspend, UMD), `sceGe_user`, `sceDisplay`, `sceCtrl`, `sceDmac`, `sceAudio`, `sceSasCore`, `sceAtrac3plus` and `sceMpeg`. A stop at an unimplemented function or a defect inside these (including an undecoded GE command, a SIGNAL behaviour, an undrawn primitive or an unsupported texture format) is implemented or fixed on the repsp submodule branch and the run repeated; added functions get probes and their commits go to the work log. A stop at a `sceUtility` call ends the task and is recorded. A defect that needs a design decision (scheduler semantics, a contract change, a decoder problem) is not fixed but raised as a question in the work log. A state that keeps running without a stop (a movie playing, a title screen waiting for input) is ended with `--max-vblanks` and reported; to see the screen after the movie the limit is set longer than the movie. If input is needed to skip the movie, scripted input that presses buttons at given vblanks is added as an app option over repsp's `hle::ctrl::SetInputSource`: `--input-script <file>`, each line `<vblank> <button names>`; script files are not committed.

## 3. Record

`docs/analysis/video.md` (new): the code path that plays a movie (threads, call order), the ring buffer size in packs, the streams registered, the decode loop and how it is paced, how decoded frames reach the screen (a GE texture or direct frame-buffer writes, and the pixel format), the PSMF header values (resolution, duration, streams), and where on the original disc the movie data comes from. Continuing `docs/analysis/first-frame.md`: the HLE order up to the stop or limit; if anything is drawn, list and primitive statistics, texture formats used and a written description of the picture (no image in the repository); the next stop NID and its name. Facts about the original game only — no location or name of the user's dump.

## 4. Verification for this task

1. Local: `redmp1 roms --headless` stops, class (a), at an unimplemented `sceUtility` NID, or ends at the vblank limit (e); no dispatch miss or deadlock.
2. Local: if a frame was presented, frame dumps are kept and their location goes to the work log (checked by the reviewer; never committed); `REPSP_FRAME_DUMP_LIMIT` keeps the number down and frames are picked where the picture changes.
3. Local: three runs are compared; audio and vblank waits follow host time, so the call order between threads may differ, and any difference is analyzed and recorded.
4. CTest `app_boot` is updated to the new end point, with a short limit if the run has become long.
5. Win64 Debug/Release and Linux x64 builds and CTest, and CI, pass; the configuration without game data (`REDMP1_HAVE_RECOMP=0`) builds without warnings.
