# 설계: 트램펄린 — 함수 사이의 전이가 호스트 스택을 쓰지 않게 (issue #33)

## 1. 요구사항

* lift된 코드에서 본문을 끝내는 전이(다른 함수로의 fall-out, 다른 함수 진입점으로의 `j`, likely 분기의 taken 경로, 간접 점프 `jr <reg>`, `jr $ra`가 점프로 쓰인 경우)는 지금 `psp_func_X(); return;` 같은 꼬리 호출로 옮겨진다. 컴파일러가 이것을 점프로 바꾸지 않으면 반복마다 호스트 스택이 쌓인다. issue #32에서 한 함수 안의 루프(472곳)는 `goto`로 고쳤지만, 여러 함수에 걸쳐 꼬리 호출로만 도는 순환이 148개 남았다(악보 재생 루프도 네 함수에 걸친다). 지금은 게스트 스레드의 64 MiB 스택이 안전망이다.
* **사용자 결정(2026-11-16)**: 트램펄린으로 해결한다. 컴파일러 최적화와 무관하게, 함수 사이의 전이가 호스트 스택을 쓰지 않아야 한다. 간접 점프로 이어지는 순환도 포함한다.
* 함수 호출(`jal`, `jalr`, 조건부 호출)의 의미는 그대로다. 호스트 스택 깊이는 게스트의 호출 깊이를 따라간다.

## 2. 방식

* **다음 함수 레지스터**: 스레드별 값 `psp_next`(실행할 다음 생성 함수의 포인터, 없으면 NULL)를 둔다. 게스트 스레드마다 호스트 스레드가 따로 있으므로 thread-local이면 된다(문맥 전환은 HLE 호출 안에서만 일어나고, "설정하고 돌아가기"와 "꺼내 실행하기" 사이에는 HLE 호출이 없다).
* **본문을 끝내는 전이**: `psp_func_Y(); return;` 대신 `psp_next = psp_func_Y; return;`(매크로 `PSP_TAIL(psp_func_Y)`). label thunk(`psp_at_Y`), 간접 점프(`psp_dispatch(addr)`의 꼬리 형태), `jr $ra`가 점프인 경우도 같은 방식이다. import(HLE) 호출은 스스로 이어지지 않으므로 지금처럼 바로 부른다.
* **실행 루프**: `psp_run(fn)`은 `fn()`을 부른 뒤 `psp_next`가 있으면 꺼내 비우고 부르기를 되풀이한다. 호스트 스택은 이 루프 한 단만 쓴다.
* **호출**: `jal`/`jalr`/조건부 호출은 `psp_run(psp_func_Y)`(호출 프레임 `PSP_CALL_BEGIN/END`는 지금처럼 바깥에 둔다). 피호출 쪽 사슬이 `jr $ra`로 끝나면(`psp_next`가 비어 있으면) 루프가 끝나고 호출한 본문으로 돌아온다.
* **host에서의 진입**: `psp_call_from_host`(repsp의 `call_guest`가 부르는 곳), 인터럽트·콜백 진입, `psp_dispatch`의 호출 형태가 모두 `psp_run`을 거친다.
* **게스트 되감기와의 관계**: `psp_ra_is_jump`가 `psp_cpu.unwind`를 설정해 여러 호출 프레임을 건너 돌아가는 경우(게스트의 `longjmp` 같은 흐름), 실행 루프는 `psp_cpu.unwind`가 설정돼 있으면 `psp_next`를 비우고 즉시 끝나야 한다. 되감기의 의미는 지금과 같아야 한다.
* **정지와 오류**: `GuardedRun`의 되감기(SEH·longjmp)는 루프 프레임을 그냥 지나간다. 정지 뒤에 `psp_next`가 남아 있지 않도록, 새 게스트 실행을 시작할 때(`psp_call_from_host`) 비운다.

## 3. 구현 위치

* **lifter 로컬 패치 0005**(`patches/psprecomp/`): `emit`의 선택 사항(예: `--trampoline`, 기본 꺼짐)으로 넣는다. 꺼져 있으면 지금 출력과 바이트 단위로 같아야 한다(upstream에 낼 수 있는 형태). 켜면 본문을 끝내는 모든 전이를 `PSP_TAIL`로, 모든 호출을 `psp_run` 경유로 낸다. 생성 헤더에 매크로와 선언을 둔다.
* **reDMP1 `src/recomp_abi/`**: `psp_next`, `psp_run`, 그리고 `psp_call_from_host`·`psp_dispatch`의 트램펄린 경로. `scripts/recomp/regenerate.py`와 `lift.json`에 트램펄린을 켜는 설정.
* **repsp**: 바뀌지 않는다(`call_guest` 계약 그대로). 바꿔야 할 것이 나오면 질문으로 올린다.
* 생성 코드를 손으로 고치지 않는다.

## 4. 측정과 검증

1. **정적 점검**: `tools/lift_audit.py`에 "본문을 끝내는 전이가 직접 호출로 남아 있지 않다" 규칙을 더한다(트램펄린 모드에서 0건). 꼬리 호출 순환(SCC) 목록은 정보로만 남는다.
2. **스택이 컴파일러와 무관함**: 생성 코드를 **최적화하지 않고**(MSVC `/Od`, GCC `-O0`) 빌드한 구성으로, 플레이 화면까지 가서 곡 구간을 오래(짧게 한 번, 길게 한 번) 돌린다. 모든 게스트 스레드의 호스트 스택 최고값이 실행 길이와 무관하게 일정해야 한다(진단 빌드의 통계). 같은 측정을 트램펄린을 끈 구성에서 해 비교한다(꺼진 쪽은 자라야 정상).
3. **성능**: 같은 입력 스크립트와 vblank 수로 트램펄린 켬/끔의 프로세스 CPU 시간(사용자 시간)과 표시 간격 통계를 Release에서 비교한다. 차이를 작업 로그에 적고, 10%를 넘으면 원인(예: 루프의 간접 호출, thread-local 접근)을 찾아 줄일 방법을 보고한다.
4. **동작**: 오프닝부터 플레이 화면까지의 입력 스크립트 실행 3회가 같은 화면에 이르고, 미발견 주소 dispatch 0건, 크래시 0건이다. 크래시 기록 장치의 `--debug-crash` 다섯 종류가 그대로 보고를 남긴다.
5. **안전망 유지**: 게스트 스레드의 64 MiB 예약과 Debug에서도 생성 코드를 최적화하는 설정은 이번에 바꾸지 않는다. 2의 결과로 둘 다 필요 없어지면 그 사실을 작업 로그에 적고, 줄일지는 사용자에게 묻는다.
6. Win64 Debug/Release(Visual Studio 생성기 포함)와 Linux x64 빌드·CTest, CI. 게임 데이터 없는 구성도 경고 없이 빌드된다.
7. 사용자가 창 모드로 곡 하나를 끝까지 플레이한다(사용자 확인).

## 5. 기록

* `patches/psprecomp/README.md`: 패치 0005의 설명(선택 사항, 끄면 출력이 같다는 사실, upstream 제출은 사용자가 정한다).
* `docs/analysis/`: 실행 경로의 변화가 게임 동작에 주는 영향이 있으면(없으면 쓰지 않는다).
* 작업 로그: 측정표(스택, CPU 시간, 표시 간격), 질문.

# Design: trampoline — transfers between functions use no host stack (issue #33)

## 1. Requirements

In lifted code, transfers that end a body (a fall-out into another function, a `j` to another function's entry, the taken path of a likely branch, an indirect jump `jr <reg>`, `jr $ra` used as a jump) are emitted as tail calls such as `psp_func_X(); return;`. When the compiler does not turn them into jumps, every iteration grows the host stack. Issue #32 fixed loops inside one function (472 places) with `goto`, but 148 cycles made only of tail calls across functions remain (the score playback loop spans four functions); the 64 MiB guest thread stack is the safety net for now. **User decision (2026-11-16)**: solve this with a trampoline, so that transfers between functions use no host stack whatever the compiler does, including cycles through indirect jumps. Calls (`jal`, `jalr`, conditional calls) keep their meaning; host stack depth follows guest call depth.

## 2. Approach

**A next-function register**: a per-thread value `psp_next` (the next generated function to run, or NULL). Each guest thread has its own host thread, so thread-local storage suffices (context switches happen only inside HLE calls, and there is no HLE call between "set and return" and "take and run"). **Transfers that end a body** become `psp_next = psp_func_Y; return;` (macro `PSP_TAIL(psp_func_Y)`) instead of `psp_func_Y(); return;` — likewise for label thunks (`psp_at_Y`), indirect jumps (the tail form of `psp_dispatch(addr)`) and `jr $ra` used as a jump. Import (HLE) calls do not continue anywhere, so they are still called directly. **The run loop**: `psp_run(fn)` calls `fn()`, then while `psp_next` is set, takes it, clears it and calls it; the host stack holds just this one loop frame. **Calls**: `jal`/`jalr`/conditional calls become `psp_run(psp_func_Y)` (the call frame `PSP_CALL_BEGIN/END` stays around it as now); when the callee's chain ends in `jr $ra` (`psp_next` empty) the loop ends and control returns to the calling body. **Entry from the host**: `psp_call_from_host` (what repsp's `call_guest` reaches), interrupt and callback entry, and the call form of `psp_dispatch` all go through `psp_run`. **Guest unwinding**: when `psp_ra_is_jump` sets `psp_cpu.unwind` to return across several call frames (a guest `longjmp`-like flow), the run loop must clear `psp_next` and end at once if `psp_cpu.unwind` is set; unwinding must mean what it means today. **Stops and faults**: `GuardedRun`'s unwinding (SEH or longjmp) passes through loop frames; so that no stale `psp_next` survives a stop, a new guest execution (`psp_call_from_host`) clears it.

## 3. Where it lives

**Local lifter patch 0005** (`patches/psprecomp/`): an `emit` option (for example `--trampoline`, off by default). Off, the output must be byte-identical to today's (a form that could go upstream); on, every body-ending transfer is emitted as `PSP_TAIL` and every call goes through `psp_run`, with the macros and declarations in the generated header. **reDMP1 `src/recomp_abi/`**: `psp_next`, `psp_run`, and the trampoline paths of `psp_call_from_host` and `psp_dispatch`; `scripts/recomp/regenerate.py` and `lift.json` turn the option on. **repsp**: unchanged (the `call_guest` contract stays); if something there must change, it is raised as a question. Generated code is never edited by hand.

## 4. Measurement and verification

1. **Static check**: `tools/lift_audit.py` gains the rule "no body-ending transfer remains a direct call" (zero in trampoline mode); the list of tail-call cycles (SCCs) stays as information.
2. **Stack independent of the compiler**: with the generated code built **unoptimized** (MSVC `/Od`, GCC `-O0`), run to gameplay and let the song stretch run long (once short, once long); every guest thread's host stack high-water must stay the same regardless of run length (diagnostic build statistics). Repeat with the trampoline off for comparison (there it should grow).
3. **Performance**: with the same input script and vblank count, compare process CPU time (user time) and presentation interval statistics in Release with the trampoline on and off. Record the difference in the work log; above 10%, find the cause (the loop's indirect call, thread-local access, ...) and report how to reduce it.
4. **Behaviour**: three scripted runs from the opening to gameplay reach the same screens, with zero undiscovered-address dispatches and zero crashes; the five `--debug-crash` kinds still leave reports.
5. **Safety nets stay**: the guest threads' 64 MiB reservation and optimizing the generated code even in Debug are not changed in this task; if item 2 shows neither is needed any more, say so in the work log and ask the user whether to reduce them.
6. Win64 Debug/Release (including the Visual Studio generator) and Linux x64 builds and CTest, and CI; the configuration without game data builds without warnings.
7. The user plays one song to the end in windowed mode (the user's check).

## 5. Record

`patches/psprecomp/README.md`: patch 0005 (an option; off gives identical output; whether to submit it upstream is the user's call). `docs/analysis/`: only if the change of execution path affects game behaviour. The work log: the measurement tables (stack, CPU time, presentation intervals) and questions.
