# 설계: 플레이 진입 — 모드 선택에서 곡 선택을 거쳐 플레이 화면까지 (issue #20)

## 1. 요구사항

* 입력 스크립트로 모드 선택 화면에서 곡 선택을 거쳐 플레이 화면까지 들어간다. 게임의 주 경로 전체가 도는지 먼저 확인하는 것이 목적이다.
* 도중의 정지와 결함은 원인이 있는 곳에서 고친다(§3). repsp 쪽은 [repsp issue #19](https://github.com/reexec/repsp/issues/19)다.
* 거친 화면과 씬 전환을 원본 게임의 사실로 `docs/analysis/`에 기록한다.

## 2. 진행 방법

* 한 화면씩 나아간다. 화면마다 (1) 입력을 기다리는 상태에서 프레임 덤프를 남기고, (2) 그 화면이 어떤 버튼을 받는지를 화면의 안내 표시와 실행 결과로 확인하고, (3) 다음 화면으로 가는 입력을 스크립트에 더한다.
* 입력 스크립트의 vblank 시점은 화면 전환(페이드, 로딩)이 끝난 뒤로 넉넉히 잡는다. 호스트 시각에 따라 전환 시점이 조금씩 달라지므로, 3회 실행에서 같은 화면에 이르는지 확인한다.
* 스크립트와 프레임 덤프는 저장소에 넣지 않는다. 스크립트의 내용(어느 vblank에 어느 버튼)은 작업 로그에 적는다.
* 끝내는 지점: 플레이 화면(노트가 내려오는 화면)에 이르러 몇 초 동안 도는 것을 확인하면 `--max-vblanks`로 끝낸다. 플레이 중의 판정과 결과 화면은 이번 범위가 아니다.

## 3. 결함을 다루는 원칙

* 원인을 추측으로 고치지 않는다. issue #18의 방법(지점 확인 → 이력 → 가설 가르기 → 확정)을 따른다.
* **게스트 쪽의 이상(assertion, 잘못된 포인터, 어긋난 스택, 돌아오지 않는 호출)은 lift 결과를 먼저 의심한다.** issue #18의 원인이 lifter의 종료 판정이었다. 해당 함수의 원본 명령열과 생성 코드를 대조하고, lifter 결함이면 `patches/psprecomp/`에 로컬 패치를 더한 뒤 재생성한다(upstream에는 아무것도 하지 않는다; 생성 코드를 손으로 고치지 않는다).
* repsp의 결함(미구현 GE 명령·텍스처 형식·블렌드 모드, HLE 동작 차이, 미구현 모드)은 submodule 브랜치 `i019-play-entry`에서 고치고 probe를 더한다.
* 다음은 고치지 말고 근거와 선택지를 작업 로그의 질문으로 올린다: 스케줄러 의미의 변경, 소비자 계약의 변경, 실제 ATRAC3plus·H.264 디코더가 있어야만 진행되는 상황(예: 게임이 디코딩된 소리의 길이나 내용에 따라 진행을 정함), 다이얼로그를 그려야만 진행되는 상황, 실행 시간이 너무 길어 호스트 시각과 무관한 빠른 실행 방식이 필요한 상황.
* 고칠 것이 여덟 건을 넘으면 멈추고 남은 것을 질문으로 올린다.

## 4. 기록

* `docs/analysis/scene-flow.md`에 이어서: 거친 화면의 순서, 화면마다 받는 입력과 넘어가는 조건, 씬을 만들고 정리하는 순서, 로딩하는 데이터 파일(원본 디스크 안의 경로)과 그 시점.
* `docs/analysis/audio.md`에 이어서: 메뉴와 플레이에서 소리를 내는 경로(SAS 음성, ATRAC3plus, 직접 PCM 출력 중 무엇을 쓰는지), 곡 데이터의 형식에 대해 실행에서 드러난 사실.
* `docs/analysis/first-frame.md`에 이어서: 새 화면들의 글 서술과 GE 통계(primitive 종류, 텍스처 형식, 블렌드 모드 중 새로 나온 것).
* lifter 패치를 더했다면 `patches/psprecomp/README.md`에 원본 명령열과 잘못 옮겨졌던 방식을 적는다.
* 원본 게임의 사실만 적는다. 사용자 덤프의 위치나 이름, 사용자 계정 이름이 든 경로는 적지 않는다.

## 5. 이번 task의 검증

1. 로컬: 입력 스크립트 실행이 플레이 화면에 이르러 vblank 한도 (e)로 끝나거나, §3의 질문 지점에서 멈춘다. 디스패치 미스, 교착, assertion이 없다.
2. 로컬: 거친 화면마다 프레임 덤프를 남기고 위치를 작업 로그에 적는다(리뷰어가 확인; 커밋하지 않는다).
3. 로컬: 3회 실행이 같은 화면에 이른다. 차이는 원인을 기록한다.
4. 고친 결함마다 probe 또는 재현 절차가 있다.
5. CTest `app_boot`는 지금의 종료 지점을 유지한다.
6. Win64 Debug/Release와 Linux x64 빌드·CTest, CI 통과. 게임 데이터가 없는 구성도 경고 없이 빌드된다.

# Design: play entry — from mode select through song select into gameplay (issue #20)

## 1. Requirements

Drive the game with an input script from the mode select screen through song select into a gameplay screen; the aim is to see first whether the game's whole main path runs. Stops and defects on the way are fixed where their cause lies (§3); the repsp side is [repsp issue #19](https://github.com/reexec/repsp/issues/19). The screens and scene transitions passed are recorded in `docs/analysis/` as facts about the original game.

## 2. Method

Advance one screen at a time. On each screen (1) keep a frame dump while it waits for input, (2) establish which buttons it takes from the hints on screen and from running it, (3) add the input that leads to the next screen to the script. Script vblank times are set comfortably after a transition (fade, loading) has finished; since transition times shift a little with host time, three runs are checked to reach the same screen. Scripts and frame dumps are not committed; the script's content (which button at which vblank) goes into the work log. End point: once a gameplay screen (notes coming down) is reached and seen running for a few seconds, the run is ended with `--max-vblanks`. Judgement during play and the result screen are out of scope.

## 3. Handling defects

No fixing by guesswork; the method of issue #18 applies (the site, the history, separating hypotheses, confirmation). **A fault on the guest side (an assertion, a wild pointer, a skewed stack, a call that never returns) is suspected first of being a lifting error**: the cause in issue #18 was the lifter's end-of-body check. The original instruction sequence of the function is compared with the generated code; a lifter defect gets a local patch under `patches/psprecomp/` followed by regeneration (nothing is done upstream; generated code is never edited by hand). A repsp defect (an unimplemented GE command, texture format or blend mode, an HLE behaviour difference, an unimplemented mode) is fixed on the submodule branch `i019-play-entry` with a probe. The following are not fixed but raised as questions in the work log, with evidence and options: a change of scheduler semantics, a change of a consumer contract, progress that requires a real ATRAC3plus or H.264 decoder (for instance the game deciding its progress from the length or content of decoded sound), progress that requires a drawn dialog, and runs so long that a fast mode independent of host time is needed. After more than eight fixes the task stops and the rest is raised as questions.

## 4. Record

Continuing `docs/analysis/scene-flow.md`: the order of screens, the input each takes and its condition for moving on, the order of scene creation and teardown, and the data files loaded (paths on the original disc) and when. Continuing `docs/analysis/audio.md`: the paths that produce sound in menus and gameplay (SAS voices, ATRAC3plus, or direct PCM output) and what the run reveals about the song data format. Continuing `docs/analysis/first-frame.md`: written descriptions of the new screens and GE statistics (primitive kinds, texture formats and blend modes that are new). A lifter patch, if added, is described in `patches/psprecomp/README.md` with the original instruction sequence and how it was mislifted. Facts about the original game only — no location or name of the user's dump and no path containing a user account name.

## 5. Verification for this task

1. Local: the scripted run reaches a gameplay screen and ends at the vblank limit (e), or stops at a question point from §3; no dispatch miss, deadlock or assertion.
2. Local: a frame dump is kept for every screen passed and their location goes to the work log (checked by the reviewer; never committed).
3. Local: three runs reach the same screen; differences are explained.
4. Every defect fixed has a probe or a reproduction procedure.
5. CTest `app_boot` keeps its present end point.
6. Win64 Debug/Release and Linux x64 builds and CTest, and CI, pass; the configuration without game data builds without warnings.
