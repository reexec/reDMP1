# 설계: 두 번째 곡의 표지가 첫 번째 곡 것으로 나옴 (issue #43)

## 1. 요구사항

* 사용자 보고(2026-11-17): 곡 선택 뒤 나오는 곡 표지 화면이 첫 번째 곡에서는 맞게 나온다. 그런데 두 번째 곡을 시작하면 첫 번째 곡의 표지가 그대로 나온다. 원래는 선택한 곡의 표지가 나와야 한다.
* 목표: 곡마다 그 곡의 표지가 나오게 한다. 게임과 무관한 결함이면 repsp에서 고친다.

## 2. 조사 (먼저)

1. **재현**: 두 곡을 연달아 고르는 입력 스크립트를 `%TEMP%` 아래에 만든다(커밋하지 않는다). 첫 곡을 끝내거나 나간 뒤 다른 곡을 고르는 순서다. 표지 화면에서 프레임 덤프나 화면 캡처를 남긴다.
2. **렌더러 비교**: 같은 스크립트를 `--renderer sw`와 `gl`로 돌린다.
   * sw는 맞고 gl만 틀리면 GL 텍스처 캐시가 같은 주소의 바뀐 내용을 알아채지 못하는 것이다.
   * 둘 다 틀리면 이미지 자체가 다시 읽히지 않는 것이다. 후보는 파일 읽기, 디코드 HLE(예: `sceJpeg`, PNG 등 게임이 쓰는 경로), 게스트 쪽 캐시다.
3. **근거 수집**: 표지 텍스처의 주소, 크기, 형식(CLUT 포함)과 두 곡에서의 텍스처 메모리 내용(해시)을 기록한다. 아울러 표지를 불러오는 HLE 호출(파일 열기·읽기, 디코드)과 인자를 정리한다.
4. **근거로 쓸 수 있는 자료**: 공개 문서(PSPSDK, uOFW)만 쓴다. PPSSPP 등 GPL 구현 코드는 보지 않는다.

## 3. 수정

* 원인 지점만 고친다. 텍스처 캐시가 원인이면 무효화 조건을 바로잡는다. 예를 들면 내용 해시, 쓰기 감지, DMA·메모리 복사·디코드 HLE가 쓴 범위의 무효화다. 이때 성능 영향(표시 간격)을 잰다.
* 원인을 재현하는 합성 probe를 넣는다. 고치기 전에는 실패하고 고친 뒤에는 통과해야 한다.

## 4. 검증

1. 두 곡 이상을 연달아 고르는 실행에서 표지가 곡마다 다르고 맞다. 덤프로 확인한다.
2. 플레이 화면까지 입력 스크립트 실행 3회, 미발견 주소 dispatch 0건, 크래시 0건, 표시 간격이 이전과 같은 범위다.
3. Win64 Debug/Release(Visual Studio 생성기 포함)와 Linux x64 빌드·CTest(repsp, reDMP1).
4. 사용자가 곡 두 개를 연달아 골라 확인한다(사용자 확인).

## 5. 기록

* `docs/analysis/`: 표지를 불러오는 경로를 원본에 대한 사실로 적는다. 사용자 파일 정보는 적지 않는다.
* 작업 로그 `docs/work-logs/20261117-i043-song-jacket.md`: 조사 결과, 측정, 질문.

# Design: the second song shows the first song's jacket (issue #43)

## 1. Requirements

**User report (2026-11-17)**: after song select, the jacket (cover) screen is right for the first song. Starting a second song shows the first song's jacket again, where it should show the selected song's.

**Goal**: each song shows its own jacket. A game-independent defect is fixed in repsp.

## 2. Investigation (first)

1. **Reproduce**: write an input script under `%TEMP%` (not committed) that picks two songs in a row: finish or leave the first, then pick another. Keep a frame dump or screen capture of the jacket screen.
2. **Compare renderers**: run the same script with `--renderer sw` and with `gl`.
   - If sw is right and gl is wrong, the GL texture cache misses changed contents at the same address.
   - If both are wrong, the image itself is not reloaded. Candidates: file I/O, a decode HLE (such as `sceJpeg`, PNG, or whatever path the game uses), or a guest-side cache.
3. **Collect evidence**: record the jacket texture's address, size and format (including the CLUT), and a hash of the texture memory for both songs. Also tabulate the HLE calls that load the jacket (file open/read, decode) and their arguments.
4. **Allowed evidence**: public documents (PSPSDK, uOFW) only. PPSSPP and other GPL implementation code is not read.

## 3. Fix

- Fix only the point of cause. If it is the texture cache, correct its invalidation conditions: a content hash, write detection, or invalidating ranges written by DMA, memory copies or decode HLEs. Measure the performance effect (presentation intervals).
- Add a synthetic probe that reproduces the cause: it fails before the fix and passes after.

## 4. Verification

1. In a run that picks two or more songs in a row, each jacket is different and correct, checked by dumps.
2. Three scripted runs to gameplay, with zero undiscovered-address dispatches, zero crashes, and presentation intervals in the same range as before.
3. Win64 Debug/Release (including the Visual Studio generator) and Linux x64 builds and CTest (repsp and reDMP1).
4. The user picks two songs in a row and checks (the user's check).

## 5. Record

- `docs/analysis/`: the path that loads the jacket, as facts about the original. Nothing about the user's files.
- Work log `docs/work-logs/20261117-i043-song-jacket.md`: findings, measurements and questions.
