# 설계: 메뉴 진입 — 타이틀 화면 뒤의 assertion 원인을 찾고 메인 메뉴로 진행 (issue #18)

## 1. 요구사항

* 타이틀 화면에서 START를 누르면 확인 효과음과 페이드아웃 뒤, 씬을 정리하는 중에 게스트가 `assertion "m_referenceCount" failed: file "Instance.cpp", line 37`을 출력하고 모듈을 스스로 내리며 끝난다(v0.0.8의 관찰). 원인을 찾아, 원인이 있는 곳에서 고친다.
* 고친 뒤 메인 메뉴 쪽으로 계속 진행한다(§3).
* 타이틀 화면의 1픽셀 폭 마젠타 선을 고친다([repsp issue #17](https://github.com/reexec/repsp/issues/17)).
* 찾은 사실은 원본 게임의 사실로 `docs/analysis/`에 기록한다.

## 2. 원인 분석 방법

원인을 추측으로 고치지 않는다. 다음 순서로 증거를 모은다.

1. **assertion 지점**: 문자열 `"m_referenceCount"`와 `"Instance.cpp"`의 주소를 찾고, 그것을 참조하는 생성 코드의 함수(assert를 부르는 곳)를 찾는다. 그 함수가 검사하는 조건(참조 횟수가 0이어야 하는지, 0이 아니어야 하는지)과 객체의 배치(참조 횟수 필드의 오프셋)를 읽는다.
2. **참조 횟수의 이력**: 실패한 객체의 주소를 얻고, 그 객체의 참조 횟수를 늘리고 줄이는 함수들을 찾아 호출 이력(호출자, 스레드, 순서)을 얻는다. 필요한 추적 수단(특정 게스트 함수 진입 기록, 특정 주소 쓰기 감시)은 환경 변수로 켜는 진단 기능으로 더한다. 진단 기능은 꺼져 있을 때 비용이 없어야 하고, 타이틀에 묶이지 않는 것은 repsp에, 타이틀 주소를 아는 것은 앱에 둔다.
3. **가설 가르기**: 이력에서 어긋난 지점을 찾고, 그 직전의 HLE 호출과 스레드 전환을 본다. 후보는 (a) HLE 반환값·부작용이 실제와 다름(이 화면에서 쓰는 ATRAC3plus, SAS, 이벤트 플래그, 세마포어, 메모리 할당 등), (b) 스케줄링 순서가 실제와 다름(깨운 스레드의 선점 시점, 우선순위, 콜백), (c) lift 결과가 원본 명령과 다름(지연 슬롯, likely 분기, FPU, 함수 경계), (d) 무음 디코더·빈 프레임처럼 의도한 단순화의 부작용이다. 각 후보를 증거로 지우거나 확정한다.
4. **확정**: 원인을 한 문장으로 적고, 그것을 보이는 최소 재현(가능하면 probe)을 만든다.

## 3. 고치는 위치와 진행 범위

* repsp의 결함이면 submodule 브랜치 `i017-menu-entry`에서 고치고 probe를 더한다.
* lifter의 결함이면 `patches/psprecomp/`의 로컬 패치로 고친다(upstream에는 아무것도 하지 않는다). 생성 코드를 손으로 고치지 않는다.
* 설계 판단이 필요한 원인(스케줄러 의미 변경, 계약 변경, 실제 디코더가 있어야만 진행됨, 다이얼로그를 그려야만 진행됨)은 고치지 말고 근거와 선택지를 작업 로그의 질문으로 올린다.
* 고친 뒤에는 issue #15와 같은 방식으로 계속 나아간다. 입력을 기다리는 다음 화면(메인 메뉴 등)에 이르면 `--max-vblanks`로 끝내고 프레임 덤프로 남긴다. 고칠 것이 여섯 건을 넘으면 멈추고 남은 것을 질문으로 올린다.
* 마젠타 선은 원인(텍스처 좌표의 끝 texel 처리, 색 키·알파 테스트, 텍스처 래핑 중 무엇인지)을 확인한 뒤 고친다. GE 사양과 다른 임시 보정은 넣지 않는다.

## 4. 기록

* `docs/analysis/scene-flow.md`(새 파일): 타이틀 화면에서 다음 화면으로 넘어가는 경로(입력 판정, 효과음, 페이드, 씬 정리와 생성의 순서, 관련 스레드와 이벤트 플래그), 참조 횟수 객체의 구조와 수명 규칙, assertion의 조건.
* `docs/analysis/first-frame.md`에 이어서: 새로 이른 화면의 서술과 통계.
* 원인이 lifter에 있었다면 `docs/analysis/` 또는 `patches/psprecomp/`의 설명에 원본 명령열과 잘못 옮겨졌던 방식을 적는다.
* 원본 게임의 사실만 적는다. 사용자 덤프의 위치나 이름, 사용자 계정 이름이 든 경로는 적지 않는다.

## 5. 이번 task의 검증

1. 로컬: 타이틀 화면에서 START를 누르는 실행이 assertion 없이 다음 화면에 이르러 vblank 한도 (e)로 끝나거나, §3의 질문 지점에서 멈춘다.
2. 로컬: 새 화면의 프레임 덤프를 남기고 위치를 작업 로그에 적는다(리뷰어가 확인; 커밋하지 않는다). 타이틀 화면의 덤프에 마젠타 선이 없다.
3. 로컬: 3회 실행을 비교하고 차이의 원인을 기록한다.
4. 원인을 보이는 probe 또는 재현 절차가 있다.
5. Win64 Debug/Release와 Linux x64 빌드·CTest, CI 통과. 게임 데이터가 없는 구성도 경고 없이 빌드된다.

# Design: menu entry — finding the cause of the assertion after the title screen and running on to the main menu (issue #18)

## 1. Requirements

Pressing START on the title screen plays the confirm sound and fades out, then during scene teardown the guest prints `assertion "m_referenceCount" failed: file "Instance.cpp", line 37` and unloads itself (observed in v0.0.8). Find the cause and fix it where it lies, then run on toward the main menu (§3). Fix the one-pixel magenta lines on the title screen ([repsp issue #17](https://github.com/reexec/repsp/issues/17)). Findings are recorded in `docs/analysis/` as facts about the original game.

## 2. Method

The cause is not fixed by guesswork; evidence is gathered in this order. (1) **The assertion site**: find the addresses of the strings `"m_referenceCount"` and `"Instance.cpp"`, the generated function that refers to them, the condition it checks (whether the count must be zero or non-zero) and the object layout (the offset of the count). (2) **The count's history**: get the address of the failing object, find the functions that raise and lower its count, and obtain their call history (caller, thread, order). Tracing aids that are needed (logging entry to chosen guest functions, watching writes to an address) are added as diagnostics switched on by environment variables, free when off; those not tied to a title go into repsp, those that know title addresses into the app. (3) **Separating hypotheses**: find where the history goes wrong and look at the HLE calls and thread switches just before. Candidates: (a) an HLE return value or side effect differs from the real one (ATRAC3plus, SAS, event flags, semaphores, memory allocation used on this screen), (b) scheduling order differs (when a woken thread preempts, priorities, callbacks), (c) the lifted code differs from the original instructions (delay slots, likely branches, FPU, function boundaries), (d) a side effect of an intended simplification such as the silent decoder or blank frames. Each is ruled out or confirmed by evidence. (4) **Confirmation**: state the cause in one sentence and build a minimal reproduction, a probe if possible.

## 3. Where to fix and how far to go

A repsp defect is fixed on the submodule branch `i017-menu-entry` with a probe. A lifter defect is fixed as a local patch under `patches/psprecomp/` (nothing is done upstream); generated code is never edited by hand. A cause that needs a design decision (scheduler semantics, a contract change, progress that requires a real decoder or a drawn dialog) is not fixed but raised as a question in the work log with evidence and options. After the fix the run continues as in issue #15: on reaching the next screen that waits for input (the main menu, for instance) it is ended with `--max-vblanks` and kept as a frame dump; after more than six fixes the task stops and the rest is raised as questions. The magenta lines are fixed after their cause is confirmed (the last texel of the texture coordinates, colour key or alpha test, or texture wrapping); no ad hoc correction that departs from the GE's behaviour.

## 4. Record

`docs/analysis/scene-flow.md` (new): the path from the title screen to the next screen (input check, sound, fade, the order of scene teardown and creation, the threads and event flags involved), the structure and lifetime rules of the reference-counted object, and the assertion's condition. Continuing `docs/analysis/first-frame.md`: a description and statistics of the newly reached screen. If the cause was in the lifter, the original instruction sequence and how it was mislifted are described in `docs/analysis/` or next to the patch. Facts about the original game only — no location or name of the user's dump and no path containing a user account name.

## 5. Verification for this task

1. Local: the run that presses START on the title screen reaches the next screen without the assertion and ends at the vblank limit (e), or stops at a question point from §3.
2. Local: frame dumps of the new screen are kept and their location goes to the work log (checked by the reviewer; never committed); the title screen dump has no magenta lines.
3. Local: three runs are compared and the cause of any difference recorded.
4. A probe or a reproduction procedure shows the cause.
5. Win64 Debug/Release and Linux x64 builds and CTest, and CI, pass; the configuration without game data builds without warnings.
