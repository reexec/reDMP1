# 설계: 자기 시작으로 돌아가는 루프의 재귀 — 플레이 중 강제 종료 (issue #32)

## 1. 요구사항

* 사용자가 곡을 끝까지 플레이하던 중 두 번 강제 종료됐다(2026-11-15). 두 번째의 정지 보고는 `Guest hardware fault: Stack overflow`(vblank 5507, 곡 도중)였다. 첫 번째 덤프에도 같은 두 생성 함수가 스택에 번갈아 쌓여 있었다. 같은 넘침이 스케줄러 잠금을 쥔 구간에서 일어나 `std::system_error(EDEADLK)`와 `abort`로 드러난 것이다.
* **원인(리뷰어 확인)**: 게임 함수 `0x0886167C`의 루프가 함수 자기 시작으로 돌아간다(`0x088616C8: j 0x0886167C`). lifter는 이것을 `psp_func_0886167C(); return;`(래퍼를 거친 자기 호출)으로 옮긴다. MSVC는 이것을 점프로 바꾸지 않아 반복마다 호스트 스택이 쌓인다. 이 루프는 곡 하나 동안 돈다(악보 재생 스레드 근처의 코드). v0.0.15에서 64 MiB 스택 예약을 없애 게스트 스레드가 기본 1 MiB로 돌아가면서 약 90초 만에 넘쳤다. 그 전에는 예약이 결함을 가리고 있었다.
* `allegrexrecomp`의 `j` 처리(`emit.c`)는 대상이 같은 본문 안에 있어도 **함수 진입점이면** `goto`가 아니라 꼬리 호출을 낸다(`owned_by(...) && !is_function(...)`). 조건 분기는 같은 경우에 이미 `goto`를 낸다. 생성 코드 전체에서 자기 함수를 부르는 본문이 472곳(함수 461개)이다.
* 이 결함을 고치고, 같은 종류(함수 경계를 넘는 루프 포함)가 다시 호스트 스택을 쌓아도 플레이가 끊기지 않게 안전망을 둔다.

## 2. 수정

1. **lifter 로컬 패치 0004**: `j`(그리고 본문을 끝내는 다른 전이)의 대상이 **현재 본문이 가진 주소**이면, 함수 진입점이라도 `goto`로 옮긴다. 그 주소에 레이블이 있어야 하므로 레이블 표시를 보장한다. 본문 시작의 진입 분기(`_entry`에 따른 내부 진입)나 시작부의 계측(`PSP_SP_*`, 추적 훅)이 `goto`로 건너뛰어도 되는지 `emit.c`에서 확인하고, 안 되는 것이 있으면 그것을 고려한 위치로 점프한다. 뒤로 가는 `goto`에는 조건 분기처럼 `PSP_LOOP`를 둔다. 패치는 이 타이틀에 묶이지 않는 일반적인 수정이어야 한다(upstream에는 사용자가 허락할 때만).
2. **점검 도구 규칙**: `tools/lift_audit.py`에 "본문이 자기 함수나 자기가 가진 진입점을 꼬리 호출한다"는 불일치 종류를 더한다. 패치 전 코드에서 472건, 패치 뒤 0건이어야 한다.
3. **함수 경계를 넘는 루프**: 두 함수가 서로 `j`로 넘나드는 루프는 `goto`로 고칠 수 없다. 점검 도구로 "꼬리 호출만으로 이루어진 순환"(호출 그래프에서 꼬리 호출 간선만의 강연결 요소)을 찾아 개수와 목록을 낸다. 고치는 방식(함수 합치기, 트램펄린 등)은 설계 판단이므로 이번에는 목록과 질문만 올린다.
4. **안전망(repsp)**: 게스트 스레드의 호스트 스레드에 명시적인 큰 스택(기본 64 MiB, 예약만; 설정 가능)을 준다. Windows와 Linux 모두. 실행 파일의 `/STACK`에는 기대지 않는다. 스케줄러 통계에 게스트 스레드별 호스트 스택 최고 사용량을 낸다([repsp issue #32](https://github.com/reexec/repsp/issues/32)).

## 3. 측정

* 진단 빌드에서 **모든 게스트 스레드**의 호스트 스택 최고 사용량을 잰다. 재는 구간은 곡 하나를 끝까지 연주하는 실행이다(입력 없이는 곡이 일찍 실패하므로, 노트를 치는 입력 스크립트를 만들거나 판정 실패로 끝나지 않는 방법을 찾는다; 못 하면 사용자가 창 모드로 확인한다). 패치 전·후, 구성별(MSVC Release/Debug, GCC Release/Debug)로 기록한다.
* 패치 뒤 주 스레드와 악보 재생 스레드의 최고값이 곡 길이와 무관하게 일정해야 한다(같은 실행을 짧게/길게 해서 비교).

## 4. 기록

* `patches/psprecomp/README.md`: 패치 0004의 설명(원본 명령열, 잘못 옮겨진 방식, 고친 방식).
* `docs/analysis/`: 악보 재생 루프의 위치와 구조(원본 게임의 사실).
* 작업 로그: 측정표, 순환 목록, 질문.

## 5. 이번 task의 검증

1. 패치 뒤 점검 도구의 자기 꼬리 호출 불일치가 0건이다. 기존 불일치(0건)와 실행 점검(호출 지점·본문 이탈 불균형 0건)이 그대로다.
2. 곡 하나를 끝까지 가는 실행에서 모든 게스트 스레드의 호스트 스택 최고값이 기록돼 있고, 곡 길이에 따라 자라지 않는다.
3. 오프닝부터 플레이 화면까지의 입력 스크립트 실행이 같은 화면에 이른다(3회).
4. 사용자가 창 모드로 곡 하나를 끝까지 플레이한다(사용자 확인).
5. Win64 Debug/Release와 Linux x64 빌드·CTest, CI 통과. 게임 데이터 없는 구성도 경고 없이 빌드된다.

# Design: loops that jump back to their own function start, lifted as recursion — forced termination during play (issue #32)

## 1. Requirements

The program terminated twice while the user was playing a song to the end (2026-11-15). The second stop report read `Guest hardware fault: Stack overflow` (vblank 5507, mid-song); the first dump had the same two generated functions alternating on the stack — the same overflow, hit inside the scheduler's locked region and surfacing as `std::system_error(EDEADLK)` and `abort`. **Cause (confirmed by the reviewer)**: a loop in game function `0x0886167C` jumps back to the function's own start (`0x088616C8: j 0x0886167C`); the lifter emits `psp_func_0886167C(); return;` (a self-call through the wrapper), which MSVC does not turn into a jump, so every iteration costs host stack. The loop runs for a whole song (code next to the score playback thread). v0.0.15 removed the 64 MiB stack reservation, guest threads fell back to the default 1 MiB and overflowed after about 90 seconds; the reservation had been hiding the defect. In `allegrexrecomp`'s handling of `j` (`emit.c`), a target inside the same body still gets a tail call rather than a `goto` **when it is a function entry** (`owned_by(...) && !is_function(...)`); conditional branches already emit `goto` in the same case. Across all generated code, 472 bodies (461 functions) call their own function. Fix this defect, and add a safety net so that defects of the same kind (including loops that span functions) do not end play even if they grow the host stack.

## 2. Fixes

1. **Local lifter patch 0004**: when the target of `j` (and of other transfers that end a body) is **an address the current body owns**, emit a `goto` even if it is a function entry, making sure the address carries a label. Check in `emit.c` whether the entry dispatch at the start of a body (interior entries by `_entry`) and start-of-body instrumentation (`PSP_SP_*`, trace hooks) may be skipped by the `goto`; if not, jump to a position that respects them. Backward `goto`s get `PSP_LOOP` as conditional branches do. The patch must be a general fix not tied to this title (upstream only when the user allows).
2. **Audit rule**: `tools/lift_audit.py` gains a mismatch kind "a body tail-calls its own function or an entry it owns" — 472 on the code before the patch, 0 after.
3. **Loops spanning functions**: a loop in which two functions jump to each other with `j` cannot be fixed with `goto`. The checker finds "cycles made only of tail calls" (strongly connected components of the call graph restricted to tail-call edges) and reports their number and list; the way to fix them (merging functions, a trampoline, ...) is a design decision, so this task only lists them and raises a question.
4. **Safety net (repsp)**: give the host threads of guest threads an explicit large stack (default 64 MiB, reserved only; configurable), on Windows and Linux, without relying on the executable's `/STACK`; report each guest thread's host stack high-water in the scheduler statistics ([repsp issue #32](https://github.com/reexec/repsp/issues/32)).

## 3. Measurement

In the diagnostic build, measure the host stack high-water of **every guest thread** over a run that plays one song to the end (without input the song fails early, so build an input script that hits notes or find a way the song does not end in failure; failing that, the user checks in windowed mode), before and after the patch and per configuration (MSVC Release/Debug, GCC Release/Debug). After the patch the high-water of the main thread and of the score playback thread must not depend on the song's length (compare short and long runs of the same thing).

## 4. Record

`patches/psprecomp/README.md`: patch 0004 (the original instruction sequence, how it was mislifted, how it is fixed). `docs/analysis/`: where the score playback loop is and how it is structured (facts about the original game). The work log: the measurement table, the cycle list, questions.

## 5. Verification for this task

1. After the patch the checker reports zero self-tail-call mismatches; the existing mismatches (zero) and the run-time check (zero imbalances at call sites and body exits) are unchanged.
2. For a run that goes to the end of a song, every guest thread's host stack high-water is recorded and does not grow with the song's length.
3. The scripted run from the opening to gameplay reaches the same screens (three runs).
4. The user plays one song to the end in windowed mode (the user's check).
5. Win64 Debug/Release and Linux x64 builds and CTest, and CI, pass; the configuration without game data builds without warnings.
