# 설계: 오디오 끊김과 느려짐, OpenGL 기본 렌더러 (issue #28)

## 1. 요구사항

* 사용자가 창 모드에서 귀와 녹화로 확인한 결함이다(2026-11-15).
  * 소프트웨어 렌더러: 소리가 전체적으로 끊기고, 모드 선택의 음악이 느리게 들린다. 녹화(모드 선택, 약 4초)의 소리는 약 20 ms 소리와 10 ms 무음이 반복됐다.
  * OpenGL 렌더러: 끊김과 느려짐이 대부분 사라진다(완전히는 아니다).
* 원인을 측정으로 확정하고 고친다. repsp 쪽은 [repsp issue #28](https://github.com/reexec/repsp/issues/28)이다.
* **사용자 결정**: 기본 렌더러를 OpenGL로 바꾼다. 창이 없거나 GL 문맥을 만들 수 없으면 소프트웨어를 쓴다.

## 2. 조사와 검증 방법

* **측정 도구**: `tools/audio_gaps.py`(표준 라이브러리만). WAV를 10 ms 단위의 에너지로 나눠, 소리 구간 사이에 낀 짧은 무음(10~50 ms)의 개수와 비율, 구간별 분포를 낸다. 음악이 원래 조용한 구간과 끊김을 구분하기 위해 "양쪽이 소리인 짧은 무음"만 센다.
* **실행 조합**: 렌더러(sw, gl) × 표시(headless, 창) × 구간(타이틀, 모드 선택, 곡 선택, 플레이). `REPSP_AUDIO_DUMP`의 장치 출력 WAV를 도구로 재고, repsp의 새 통계(wake latency, 끌어가기 단위, 큐 깊이, underrun, GE 리스트 실행 시간)를 함께 기록한다. 창 모드를 실행할 수 없는 환경이면 headless 수치만 내고 그 사실을 적는다(창 모드는 리뷰어와 사용자가 확인한다).
* **순서**: 고치기 전의 수치 → repsp의 수정(가설별로 하나씩) → 수정마다 같은 조합으로 다시 측정. 어느 수정이 어느 수치를 얼마나 바꿨는지 표로 남긴다.
* **느려짐**: 모드 선택의 음악(SAS 음원, 좌우 두 음성)이 일정 시간 동안 낸 샘플 수가 표본화 주파수 × 시간과 맞는지 SAS 출력 WAV와 통계로 확인한다. 끊김이 사라지면 느려짐도 사라지는지 본다. 남으면 원인을 따로 가린다.

## 3. 앱 변경

* 기본 렌더러: `--renderer`를 주지 않으면 `gl`을 시도하고, 실패하면 이유를 한 줄로 알리고 `sw`로 계속한다. `--headless`만 주고 렌더러를 지정하지 않으면 `sw`다(CI와 CTest는 그대로).
* 오디오 지연 설정: repsp가 중간 버퍼를 더하면 `--audio-latency-ms <n>`으로 목표 깊이를 정한다(기본값은 repsp의 기본값).
* 정지 보고에 오디오 통계(실제 underrun, 끌어가기 단위, 중간 버퍼 깊이)와 wake latency 요약을 더한다.
* CTest `app_boot`는 `--headless`이므로 `sw` 그대로다.

## 4. 기록

* `docs/analysis/audio.md`에 이어서: 게임의 사운드 스레드 구조(스레드, 우선순위, 한 번에 내는 샘플 수, 대기 방식)와 화면 그리기 스레드의 리스트 크기 — 원본 게임의 사실만.
* `docs/guides/running-and-tracing.md`: 기본 렌더러, 새 옵션, 측정 도구의 사용법.
* 작업 로그: 조합별 고치기 전·후 수치, 남은 끊김과 그 원인(또는 모른다는 사실), 사용자가 확인할 화면.

## 5. 이번 task의 검증

1. headless에서 sw와 gl 모두, 타이틀부터 플레이 화면까지의 장치 출력 WAV에 "양쪽이 소리인 짧은 무음"이 없다(0개). 남으면 위치와 원인을 기록한다.
2. underrun 통계가 WAV의 무음과 맞는다(무음이 있으면 0이 아니다).
3. 모드 선택 음악의 출력 샘플 수가 시간과 1% 안에서 맞는다.
4. 플레이 화면까지의 입력 스크립트 실행이 같은 화면에 이른다. 3회 실행을 비교한다.
5. 기본 렌더러가 창 모드에서 `gl`이고, GL을 쓸 수 없을 때 `sw`로 내려간다.
6. Win64 Debug/Release와 Linux x64 빌드·CTest, CI 통과. 플러그인 구성의 CTest도 Win64에서 통과한다.
7. 최종 확인은 사용자가 창 모드로 듣는다(sw와 gl 모두).

# Design: audio gaps and slowness, OpenGL as the default renderer (issue #28)

## 1. Requirements

Defects the user confirmed by ear and from a recording in windowed mode (2026-11-15). Software renderer: all sound has gaps and the mode select music seems slow; the recording (mode select, about four seconds) repeated about 20 ms of sound and 10 ms of silence. OpenGL renderer: the gaps and slowness are mostly gone, not entirely. Causes are confirmed by measurement and fixed; the repsp side is [repsp issue #28](https://github.com/reexec/repsp/issues/28). **User decision**: the default renderer becomes OpenGL, with software used when there is no window or no GL context can be created.

## 2. Investigation and verification

**Measuring tool**: `tools/audio_gaps.py` (standard library only) splits a WAV into 10 ms energy windows and reports the number and share of short silences (10 to 50 ms) lying between sounding stretches, with their distribution over time; to tell gaps from passages where the music is simply quiet, only "short silences with sound on both sides" are counted. **Run matrix**: renderer (sw, gl) × presentation (headless, windowed) × stretch (title, mode select, song select, gameplay); the device output WAV from `REPSP_AUDIO_DUMP` is measured with the tool, and repsp's new statistics (wake latency, pull size, queue depth, underruns, GE list run time) are recorded alongside. Where windowed runs are not possible only headless figures are given, and that is stated (windowed mode is checked by the reviewer and the user). **Order**: figures before any fix, then repsp's fixes one hypothesis at a time, measuring the same matrix after each; a table records which fix changed which figure by how much. **Slowness**: whether the mode select music (a SAS source, two voices left and right) outputs the number of samples that the sample rate times the elapsed time requires is checked from the SAS output WAV and the statistics; whether the slowness disappears with the gaps is observed, and if it remains its cause is separated.

## 3. App changes

Default renderer: without `--renderer` the app tries `gl` and, failing that, states the reason in one line and continues with `sw`; `--headless` without a renderer option means `sw` (CI and CTest unchanged). Audio latency: if repsp adds the intermediate buffer, `--audio-latency-ms <n>` sets its target depth (default: repsp's default). The stop report gains audio statistics (real underruns, pull size, intermediate buffer depth) and a wake latency summary. CTest `app_boot` is `--headless` and so stays on `sw`.

## 4. Record

Continuing `docs/analysis/audio.md`: the structure of the game's sound threads (threads, priorities, samples per output, how they wait) and the size of the drawing thread's lists — facts about the original game only. `docs/guides/running-and-tracing.md`: the default renderer, the new options and how to use the measuring tool. The work log: figures before and after for each combination, the gaps that remain and their cause (or the fact that it is unknown), and the screens for the user to check.

## 5. Verification for this task

1. Headless, with both sw and gl, the device output WAV from the title to the gameplay screen has no "short silence with sound on both sides" (zero); anything remaining is recorded with its position and cause.
2. The underrun statistic agrees with the WAV's silences (non-zero when there are any).
3. The mode select music's output sample count matches elapsed time within 1%.
4. The scripted run to the gameplay screen reaches the same screens; three runs are compared.
5. The default renderer in windowed mode is `gl`, falling back to `sw` when GL is unavailable.
6. Win64 Debug/Release and Linux x64 builds and CTest, and CI, pass; CTest in the plugin configuration passes on Win64.
7. The final check is the user listening in windowed mode (both sw and gl).
