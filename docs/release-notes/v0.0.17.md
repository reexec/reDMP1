# reDMP1 v0.0.17

Crash capture and analysis: leaving enough behind to analyze the next forced termination at once.

Issue [#31](https://github.com/reexec/reDMP1/issues/31): each run keeps a run log (`run.log`) and an input recording (`input_recording.txt`, on by default) in `crashes/<time>/` under the per-user data directory, adding a crash report and minidump when it crashes (folders of runs without a crash are removed); `--crash-dir`, `--no-input-record`, and the development option `--debug-crash <kind>`; PDBs for MSVC Release builds; the analysis tool `tools/analyze_crash.py` (resolves a dump and report with the PDB, without a debugger, into functions and line numbers and the type and message of a C++ exception); `docs/guides/crash-reporting.md` (what to do after a crash); repsp pinned at v0.0.16 (`bf83a21`). Commits from `a9b9a2f` on task branch `i031-crash-analysis`, squashed into this release's merge commit.

The first case: the first forced termination on 2026-11-15 (`abort`, `std::system_error(EDEADLK)`) was the host stack overflow fixed in v0.0.16, hit inside the scheduler's locked region. The same situation now leaves a crash report reading "Stop/fault while holding scheduler lock: <original reason>" (the same on Windows and Linux).

Cost in normal runs: presented frames and audio statistics were the same with the capture on and off. Guest function entry recording is on only in the diagnostic build (`REDMP1_TRACE_GUEST=ON`).

Known limits: 148 tail-call cycles across functions (to be solved by the trampoline, [#33](https://github.com/reexec/reDMP1/issues/33)). Dialogs are not drawn on screen. Save data is plaintext.

Verified: Win64 Debug/Release (Ninja and Visual Studio) CTest 35/35, the configuration without game data 32/32, Linux x64 (WSL Ubuntu 24.04) Debug/Release CTest 35/35; all five `--debug-crash` kinds produce a report, dump, log and input recording.
