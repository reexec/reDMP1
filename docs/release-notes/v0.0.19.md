# reDMP1 v0.0.19

The trampoline: transfers between functions use no host stack.

Issue [#33](https://github.com/reexec/reDMP1/issues/33): by the user's decision (2026-11-16), transfers that end a body (fall-outs into another function, `j`, likely branches, indirect jumps, `jr $ra` used as a jump) now record the next function and return (`PSP_TAIL`), and the run loop `psp_run` calls it. This is the local lifter patch 0005's `--trampoline` (off by default; off, the output is byte-identical to before the patch) and the recomp ABI's `psp_next`/`psp_run`. Guest unwinding (`psp_cpu.unwind`) keeps its meaning. `lift_audit.py` gains the rule "no body-ending direct call" (zero). `REDMP1_RECOMP_UNOPT` (off by default) builds the generated code unoptimized for measurement. repsp is unchanged. Commits from `72929c9` on task branch `i033-trampoline`, squashed into this release's merge commit.

Measured (**confirmed**, generated code unoptimized, 2,400 and 3,600 vblanks at gameplay): with the trampoline, `user_main` 20 KiB, `ScorePlayerThread` 12 KiB and `stream_sound_poll_thread` 12 KiB at both lengths; without it, 24,576 KiB, 2,172 → 2,868 KiB and 356 → 464 KiB. The stack no longer grows with run length, whatever the compiler does. Release is not slower: with the same play script it presents slightly more frames than v0.0.18 (1,263-1,269 against 1,209-1,246); three runs reached the same screens with zero undiscovered-address dispatches, and the five `--debug-crash` kinds leave reports.

Known limits: the guest threads' 64 MiB stack reservation and optimizing the generated code in Debug stay as safety nets (whether to reduce them is decided separately). Dialogs are not drawn on screen. Save data is plaintext.

Verified: Win64 Release (FFmpeg plugin) and Debug (Visual Studio generator), and Linux x64 Debug/Release, build and CTest.
