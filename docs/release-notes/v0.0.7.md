# reDMP1 v0.0.7

Video wired in: through the opening movie's playback loop to the first picture ("NOW LOADING"), stopping at the first save data call.

Issue [#13](https://github.com/reexec/reDMP1/issues/13): repsp's sceMpeg HLE registered in the app, mpeg statistics in the stop report; `--input-script`, which presses buttons at given vblanks; CTest `app_boot` updated to end at a vblank limit during movie playback; a 64 MiB host stack reserved in the MSVC build; `docs/analysis/video.md` (the playback path, ring buffer, streams, and how frames reach the screen); repsp pinned at v0.0.7 (`f0675fe`). Commits from `a4d028c` on task branch `i013-mpeg`, squashed into this release's merge commit.

Measured (**confirmed**): the game builds a 3,840-pack ring buffer, registers one AVC and one ATRAC stream, and decodes the 480x272 opening movie alternately into two RGBA8888 frame buffers shown directly with `sceDisplaySetFrameBuf` (not through GE). Without input the playback continues and the run ends at the vblank limit. Pressing START releases the movie resources, draws a "NOW LOADING" banner at the right of a black background with GE lists (3 triangle strips, 3 sprites, 411,657 pixels), and stops at `sceUtility` `sceUtilitySavedataInitStart` (`0x50C4CD57`). In both scenarios three runs give the same stop point and the same display, GE and mpeg statistics (only the call counts of the sound polling thread, which follows host time, differ).

Known limits: video is black frames and audio silence (user decision; decoders are chosen later). In Debug builds tail calls in lifted code grow the host stack, so the stack reservation was raised; the real fix remains a lifter task.

Verified: build and CTest 30/30 (with game data) on Win64 Debug/Release and Linux x64 (WSL Ubuntu 24.04), and 24/24 in the configuration without game data.
