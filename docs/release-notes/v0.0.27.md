# reDMP1 v0.0.27

Chart and music start together, in time with a music offset of 0.

Issue [#54](https://github.com/reexec/reDMP1/issues/54):

- **Report**: after v0.0.26 the music still needed about 100 ms of offset.
- **Cause**: before starting its chart clock, the game waits for its music thread, which checks for requests every 100 ms, with up to 1000 calls to `sceKernelDelayThread(10 µs)`. In repsp those 1000 calls took 29 ms, so the chart started 60-70 ms before the music.
- The chart clock (the event sequencer in `ScorePlayerThread`) and this wait loop were found in the game code; see `docs/design/20261121-i054-delaythread-minimum.md`.
- **Fix**: repsp v0.0.26 makes short delays last at least 200 µs ([reexec/repsp#57](https://github.com/reexec/repsp/issues/57)).
- The music offset is now right at its default of 0, and is for differences between output devices.
- Local psprecomp patch 0006 has been submitted upstream ([sp00nznet/psprecomp#38](https://github.com/sp00nznet/psprecomp/pull/38)).

Commits from `9dd310f` on task branch `i054-music-latency-2`, squashed into this release's merge commit.

Measured (windowed, same input script):

- Chart start and the first music block 0.3 ms apart (59 ms before).
- No unresolved-address dispatches, no crashes.
- Mean present interval 18.9 ms.

Confirmed by the user with an offset of 0.

Known limits: dialogs are not drawn on screen. Save data is plaintext.

Verified: Win64 Release (Visual Studio generator), Win64 Ninja Debug/Release and Linux x64 Debug/Release, build and CTest.
