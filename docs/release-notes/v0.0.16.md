원인(**확인됨**): 게임 함수 `0x0886167C`의 루프가 함수 자기 시작으로 돌아간다(`j 0x0886167C`). lifter는 이것을 자기 호출로 옮겼고, MSVC가 점프로 바꾸지 않아 반복마다 호스트 스택이 쌓였다. 이 루프는 악보 재생 스레드 근처에서 곡 하나 동안 돈다. v0.0.15에서 64 MiB 예약을 없앤 뒤 게스트 스레드의 기본 1 MiB를 곡 도중(약 90초)에 넘겼다. 첫 번째 강제 종료는 같은 넘침이 스케줄러 잠금을 쥔 구간에서 일어나 `abort`로 드러난 것이다. 같은 모양의 루프가 461개 함수에 472곳 있었고 모두 고쳤다(점검 도구로 패치 전 472건, 패치 후 0건).

결정(사용자, 2026-11-16): 여러 함수에 걸쳐 꼬리 호출로만 도는 순환이 148개 남는다(악보 재생 루프도 네 함수에 걸쳐 있다). 이것은 **트램펄린**으로 해결한다: 본문을 끝내는 전이가 다음에 실행할 함수를 돌려주고 바깥 반복문이 부르는 방식으로, 컴파일러와 무관하게 함수 간 전이가 호스트 스택을 쓰지 않게 한다. 별도 task로 진행하며, 그때까지 64 MiB 예약이 안전망이다.

사용자 확인(2026-11-16, 창 모드): 곡 하나를 끝까지 플레이했다.

알려진 한계: 위의 순환 148개(트램펄린 task에서 해결). 스케줄러 잠금을 쥔 구간의 정지·오류가 정지 보고 없이 `abort`로 끝나는 결함은 크래시 기록 작업([#31](https://github.com/reexec/reDMP1/issues/31))에서 다룬다. 다이얼로그를 화면에 그리지 않는다. 세이브 데이터는 평문이다.

검증: Win64(`scripts\build_win64.bat Release ffmpeg` CTest 35/35; Visual Studio Debug/Release는 Antigravity 확인)와 Linux x64(WSL Ubuntu 24.04, Debug/Release CTest 34/34, 경고 0).

# reDMP1 v0.0.16

Forced termination during play fixed: a lifter defect lifted loops that return to their own start as recursion.

Issue [#32](https://github.com/reexec/reDMP1/issues/32): local lifter patch `0004-j-owned-target-goto` — a `j` to an address inside the same body becomes a `goto` even at a function entry (regeneration required); the checker gains a self-tail-call rule and a list of tail-call cycles; per-guest-thread host stack statistics in the diagnostic build; `docs/analysis/score-playback.md` (the score playback loop); repsp pinned at v0.0.15 (`1a69cee`; a 64 MiB host stack for guest threads). Commits from `60266d5` on task branch `i032-self-loops`, squashed into this release's merge commit.

Cause (**confirmed**): a loop in game function `0x0886167C` returns to the function's own start (`j 0x0886167C`). The lifter emitted a self-call, MSVC did not turn it into a jump, and every iteration cost host stack. The loop runs for a whole song next to the score playback thread; after v0.0.15 removed the 64 MiB reservation it overflowed the guest thread's default 1 MiB mid-song (about 90 seconds in). The first forced termination was the same overflow hit inside the scheduler's locked region, surfacing as `abort`. Loops of the same shape existed at 472 places in 461 functions, all fixed (472 checker findings before the patch, 0 after).

Decision (user, 2026-11-16): 148 cycles made only of tail calls across functions remain (the score playback loop itself spans four functions). They will be solved with a **trampoline**: transfers that end a body return the function to run next and an outer loop calls it, so transfers between functions use no host stack whatever the compiler does. This is a separate task; until then the 64 MiB reservation is the safety net.

User check (2026-11-16, windowed): one song played to the end.

Known limits: the 148 cycles above (to be solved by the trampoline task). A stop or fault inside the scheduler's locked region ending in `abort` without a stop report is handled in the crash capture work ([#31](https://github.com/reexec/reDMP1/issues/31)). Dialogs are not drawn on screen. Save data is plaintext.

Verified: Win64 (`scripts\build_win64.bat Release ffmpeg` CTest 35/35; Visual Studio Debug/Release checked by Antigravity) and Linux x64 (WSL Ubuntu 24.04, Debug/Release CTest 34/34, zero warnings).
